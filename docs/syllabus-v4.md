## 一、课程定位与能力目标

**定位**：面向「用 AI 写过 Web 页面、但看不懂生成代码、无法约束 AI」的零 Web 基础学生。系统讲授主流框架（FastAPI / React）**完成核心任务所需的概念、常用写法与执行机制**；不追求 API 覆盖率，不以记忆参数配置为目标。每个常用写法都要回答两件事：**它替我做了什么**，以及**它不负责什么**。

**讲给学生的一句话**：
> 人能看出 AI 代码不对劲，靠的不是背规则，而是见过足够多的正确实现。所以这门课先让你写对，再让你看懂，最后才让你评审。

**结业时的四种能力（考核必须四种都覆盖）**

| 能力 | 标准 |
|---|---|
| ① 看懂一个正确实现 | 对给定代码说出每段职责、位于链路哪一层、框架替它做了什么 |
| ② 完成一个小改动 | 在既有工程中新增/修改一个端点或组件，不破坏现有回归 |
| ③ 解释运行结果 | 运行前能作出**有明确条件的**可检验预测，运行后用报文 / 日志 / 断点 / SQL 解释差异 |
| ④ 识别并处理一个问题 | 定位缺陷所在层、说明后果、给出修复与验证证据 |

**技术目标（深度不缩水）**：请求全链路 · 框架执行机制 · 数据建模与 SQL · ORM 与事务 · 并发写正确性 · 测试与 CI · 前端构建链路 · React 状态模型 · 请求生命周期 · 认证授权 · Web 安全基线 · AI 服务集成与上线。

## 二、五条教学判据

**判据 1 · 每课有一个核心解释目标**
明确本课要让学生能解释什么，并列出支撑它所必需的概念。支撑概念可以不止一个，但不并列展开互不依赖的多个复杂机制。

**判据 2 · 模板必须标注理解边界**
每个教师提供的模板在课件中标注为下列之一：

| 标注 | 含义 | 后果 |
|---|---|---|
| **要求解释** | 学生须能说明它做了什么、为什么这样写 | 课堂必须安排对应铺垫；可进口试与考核 |
| **要求会用** | 学生须能调用、能按规格修改参数或字段 | 课堂演示一次用法即可；考核只考用法 |
| **黑盒** | 按原样使用，不要求解释内部实现 | **不进口试，不进考核**；不得布置要求修改其内部的作业 |

**判据 3 · 关键观察点先预测**
每课选 2–3 个可检验的观察点让学生先写预测，再运行对照。**预测题必须写全条件**，使学生能据条件推理，而不是猜教师预设的答案。安装依赖、启动服务、跑回归不作预测。

**判据 4 · 第一个正例之后，学生要作一次独立的小决定**

> **限定**：在固定需求与公开契约下，学生独立选择**实现方式**、构造**测试输入**、判断**给定情境属于哪一类**，并解释选择。
> 若要比较其他契约方案，放在**隔离练习**中进行，不改动主线工程的公开契约。

**判据 5 · 常用写法卡**
每课一张，收录**本课程限定场景中的常用路径**（5–8 条），每条附：
- 这是框架/浏览器/数据库替你做的：___
- 出错时通常错在哪一侧：___
- **本课必须知道的一条边界**：___

卡片基线由教师提供并核验，学生每课补一个自己的例子或一处判断。它不是万能规则表。

### 第 1 课 ⬤｜第一个 Web 接口：从地址栏到你的函数

**目标句**：你能启动一个服务、访问一个接口、改掉它的返回，并说出这次访问经过了哪些环节。

- **前置卡**：Python 函数与装饰器语法形状；命令行启动程序；DevTools 打开方式
- **核心解释目标**：地址栏的一串字符，怎么变成你函数的参数，又怎么变回屏幕上的字
- **支撑概念**：ASGI 服务器与应用框架的职责划分、路由、路径参数、返回值序列化

**常用写法卡 #1**
应用对象 / `@app.get` 声明路由 / 路径参数写进函数签名 / 返回 dict 自动变 JSON / `uvicorn` 启动 / `raise HTTPException(404)` / DevTools Network 看一次请求。
→ **Uvicorn（ASGI 服务器）替你做的**：监听端口、接收连接、解析 HTTP 报文、按 ASGI 协议交给应用。
→ **FastAPI（应用框架）替你做的**：匹配路由、把路径字符串转成参数、调用你的函数、把返回值序列化成 JSON 响应。
→ 出错通常在：路径没匹配上（框架侧 404）、函数内部异常（你这侧 500）。
→ **必须知道的边界**：能返回 200 不代表业务结果正确；资源不存在要显式返回 404，不能返回 200 加一个空对象。

| 分钟 | 环节 |
|---|---|
| 5 | 看一眼学期末成品，说明今天做第一步 |
| 15 | 浏览器 / 服务器 / 数据三方图；**在图上标出 Uvicorn 与 FastAPI 各管哪一段**；URL 构成 |
| 20 | 教师现场写 `GET /questions` 返回硬编码列表，逐行讲「启动之后是谁调用了我的函数」 |
| 25 | **学生任务**：加 `GET /questions/{qid}`；先按自己的想法处理「找不到」的情况并运行，再对照 404 的做法解释差异 |
| 15 | 加一行日志 + 打一个断点，看见参数是怎么来的 |
| 10 | 学生画请求链路图 v1（五个框足够） |
| 5 | 出口小题 + 作业 |
| **95** | **合计**（+5 缓冲） |

**关键观察点（先预测）**
① 断点停下时，`qid` 参数**在函数签名中未标注类型**的情况下，是字符串 `"3"` 还是整数 `3`？若标注为 `int` 呢？
② 访问一个**应用中完全没有声明**的路径，404 由谁产生——你的代码还是框架？

**AI 角色（阶段一）**：让 AI 解释 `@app.get("/questions/{qid}")` 这一行做了什么，用断点验证它说得对不对。

**作业（A 档）**：M0 三接口 + 链路图 v1 + 一次断点截图 + 概念三问表。

**想再往下挖**：用手写 `socket` 收一次 HTTP 请求，看看 ASGI 服务器替你省掉了什么。

### 第 2 课 ⬤｜HTTP 的两端：用一个最小页面接上接口

**目标句**：你能写一个页面把接口数据显示出来，并说明加载中、成功、空、失败四种情况分别怎么来。

- **前置卡**：`querySelector`、事件监听、`textContent`、`await` 的形状
- **核心解释目标**：`fetch` 之后你手里拿到的到底是什么——响应对象 / 正文 / 解析结果，各自怎么失败
- **数据来源**：教师随第 1 课课后包提供 SQLite 数据模块（含 `search(keyword, page, page_size)`），**标注为「要求会用」**，学生调用不实现

**常用写法卡 #2**
`form` + `label` + `button` / `<script defer>` / `await fetch(url)` → **检查 `res.ok`，不 ok 则主动抛错** → `await res.json()` → 检查结构 → 渲染 / 用户内容用 `textContent` 输出 / loading-success-empty-error 四态骨架。
→ 浏览器替你做的：DNS、建连、发报文、解析响应头。
→ 出错通常在：把「服务器返回 500」当成「网络失败」；在数据还没到时就读属性。
→ **必须知道的边界**：**`fetch` 不会仅因为 HTTP 错误状态码而 reject**；网络失败、请求被取消（通常为 `AbortError`）、请求配置非法或被浏览器策略阻止等情况可能使请求失败。应分别判断：请求本身失败、检查 `res.ok` 后主动抛出的 HTTP 错误、`.json()` 的正文解析失败，不能把所有 `catch` 都解释成断网。

| 分钟 | 环节 |
|---|---|
| 5 | 回顾与目标 |
| 12 | 方法语义与状态码三类（2xx / 4xx / 5xx，不铺全表） |
| 18 | 教师构建一次完整 fetch → 判断 → 解析 → 渲染 |
| 25 | **学生任务**：补齐四态搜索页；按给定的四态文案规格实现，自己选择 DOM 结构与渲染方式，并构造触发 empty 的查询输入 |
| 15 | 三种失败对照：后端 500 / 返回非 JSON / 断网 |
| 10 | 用户内容渲染：`textContent` 与 `innerHTML` 的区别（埋 XSS 点） |
| 10 | 心智图更新 + 出口小题 |
| **95** | **合计**（+5 缓冲） |

**关键观察点（先预测）**
① 代码写成 `const data = await (await fetch(url)).json()`，**没有检查 `res.ok`**，后端返回 500 且正文为 JSON 错误体时，`catch` 会被触发吗？界面会显示什么？
② 同样的代码，后端返回 500 且正文是 HTML 错误页时，结果有何不同？是在哪一步失败的？

**AI 角色（阶段一）**：让 AI 解释那三行 fetch 的失败路径，再用三种故障实际核对。

**作业（A 档）**：四态搜索页 + 三类失败截图 + 一次 AI 解释核对记录。

**想再往下挖**：同一次请求用 `curl -v` 发一遍，对照 DevTools 看报文差异。

> **教师交接**：本页是一次性最小页面，第 5 课被 SSR 取代、第 10 课起被 React 取代——**要对学生讲明，避免以为白写了**。缓存、ETag、Cookie 不在本课出现。页面与 API 同源。

### 第 3 课 ⬤｜FastAPI 正式入门：参数、模型与返回值

**目标句**：你能用 Pydantic 正常实现列表查询和创建接口，并说出非法输入被挡在了哪里。

- **前置卡**：类型注解、类属性、JSON 结构
- **核心解释目标**：**校验发生在你的端点函数之前**——非法输入根本没进来
- **支撑概念**：三类参数位置、In/Out 模型、422 结构

**数据访问的分工（本课新增明确）**

| 提供物 | 标注 | 学生要求 |
|---|---|---|
| 参数化查询/插入骨架（含占位符绑定、显式字段映射、`lastrowid`/`RETURNING` 取回新 id） | **要求解释** | 读懂绑定关系、按字段改写、接进端点 |
| 连接获取与关闭 | 要求会用 | 第 4 课才收进依赖 |

### 第 4 课 ◐｜依赖注入与统一错误出口

**目标句**：你能把重复的资源获取收敛进一个依赖，并让所有错误从同一个出口返回。

- **前置卡**：第 3 课三端点；`yield` 的形状
- **核心解释目标**：依赖什么时候求值、资源什么时候释放、**提交与响应的先后**

**课程事务主路径（本版明确选定，写入交接表）**

> **主路径：由服务层业务用例入口拥有事务边界并显式提交，端点拿到结果后再返回。**
> 依赖只负责提供连接/会话与最终清理，**不在依赖退出阶段提交**。
> 第 7 课引入 Session 后沿用同一条：一个业务操作统一控制事务，内部辅助函数与数据访问层只做读写、不各自提交；端点只做 HTTP 翻译。
> 其他方案（function 作用域依赖提交等）放参考层，**不在主线示例中出现**，避免学生从不同示例里学到三种提交位置。

**常用写法卡 #4**
`Depends(get_conn)` / `yield` 依赖的 setup-teardown 形状 / **服务层显式提交** / 自定义业务异常类 / `@app.exception_handler` 统一翻译成 HTTP / 统一四字段错误体 / 结构化日志带 request-id（中间件模板，**标注「要求解释」**）。
→ 框架替你做的：按签名解析依赖、同一请求内复用同一依赖结果、在依赖退出时执行清理、把未捕获异常兜成 500。
→ 出错通常在：业务层里写死 HTTP 状态码；把本该在响应前完成的事放进清理阶段。
→ **必须知道的边界**：**默认 request 作用域依赖的退出代码在响应发出之后执行**。因此如果把提交放在依赖退出阶段，「200 成功」并不能保证数据已落库。本课程统一在服务层显式提交：**成功响应晚于提交完成，但失败响应不意味着没有发生写入**。

### 第 8 课 ◐｜写操作的正确性：为什么票会丢

**目标句**：你能复现并发投票导致的丢失更新，用条件更新修复，并解释 409 的含义。

- **前置卡**：第 7 课事务边界；第 3 课错误响应
- **核心解释目标**：两个人同时投票，票为什么会丢

**常用写法卡 #8**
版本字段 `version` / 原子 `UPDATE ... SET vote_count=vote_count+1, version=version+1 WHERE id=? AND version=?` / 用受影响行数或 `RETURNING` 结果判断是否更新成功 / 错误体带 `code`（`version_conflict` / `duplicate_title`）/ 幂等的定义：重复请求的预期效果。
→ 数据库替你做的：单条 UPDATE 的原子性。
→ 出错通常在：读—改—写三步之间被别人插队。
→ **必须知道的边界**：**版本冲突不是成功，不能自动换成新版本重发**——那等于把用户没看到的状态当成他同意了。**更新影响 0 行有两种原因**：资源不存在与版本不匹配，必须分开判断（前者 404，后者 409）；用 `RETURNING` 取回结果判断同样可靠，不规定唯一写法。

|---|---|
| 5 | 目标 |

### 第 12 课 ◐｜请求生命周期：竞态、错误与服务端数据

**目标句**：你能正确完成一次读取，并保证响应回来时不会更新错界面；能把第 11 课的表单接上真实提交。

- **前置卡**：第 2 课四态；第 11 课 state、事件与表单 UI
- **核心解释目标**：响应回来时，界面还是不是当初发请求的那个界面
- **开场回收**：**Effect 闭包捕获的是那次 render 的值**（与第 11 课的「事件处理函数看到那次的值」是同一类现象的两个位置）

**常用写法卡 #12**
`useEffect` 用于同步外部系统 / 依赖数组与 cleanup / 四态渲染 / 过期结果保护（cleanup 置标志或 `AbortController`）/ TanStack Query 的 `queryKey` 必须包含全部影响结果的参数 / `useMutation` 成功后失效相关数据并回读 / **HTTP 失败必须在适配器里转成 reject**。
→ Query 替你做的：缓存、请求去重、按 key 隔离数据身份、失效后重新获取。
→ 出错通常在：把错误响应当成功数据缓存；key 漏了参数导致串数据。
→ **必须知道的边界**：**取消客户端等待，不保证服务器停止执行，也不回滚已经发生的写操作**；写请求超时或断连时，提交结果可能未知，不能据此断言未写入或直接重试。

### 第 13 课 ◆｜URL 与状态归属：完成可恢复的 SPA ｜**交付 M4**

- **核心解释目标**：这份状态的唯一真相在哪

### 第 14 课 ⬤｜认证与授权：服务器凭什么知道你是谁

**目标句**：你能跑通注册、登录、识别用户、退出的完整正常流程，并说出每一步靠什么记住身份、每个动作凭什么被允许。

- **前置卡**：第 4 课依赖注入；第 3 课校验
- **核心解释目标**：服务器凭什么知道你是谁，以及「知道你是谁」和「允许你做这件事」是两件事

> **本版新增**：本课模板**自带 CSRF 安全基线**（SSR 表单带同步器 token，SPA 写请求带自定义头且服务端强制校验，Cookie 设 `SameSite=Lax`）。**不让学生先交付一个故意缺防护的版本**；第 15 课负责解释这套基线为什么有效并验证其拒绝路径。

**常用写法卡 #14**
注册：唯一约束 + 强度校验 + bcrypt/Argon2 推荐参数 + 不泄漏账号是否存在 / 登录成功后重签会话 ID / Cookie 四属性 `HttpOnly` `Secure` `SameSite` `Max-Age` 逐项配置并在 Application 面板验证 / `get_current_user` 与 `require_login` 依赖 / **动作级权限依赖：`require_can_edit(question)`** / 401 vs 403 vs 404 判据 / 写操作遇 401 时保留输入、提示并引导登录，不做全局无条件跳转 / `credentials:'include'` / **CSRF 基线随认证一起上线**。
→ 浏览器替你做的：按作用域与策略自动携带 Cookie。
→ 出错通常在：只在前端隐藏按钮当权限；登出只清前端状态。
→ **必须知道的边界**：**认证 ≠ 授权**。登录只证明「你是谁」；每个受保护操作都要独立判断**当前用户是否有权对当前对象执行当前动作**。本课程的规则是：**问题与回答的详情为公开读取，不要求拥有对象；修改与删除仅作者可做；管理员另有角色规则。** 在列表页过滤掉别人的数据，不等于详情与修改接口受到保护。

### 第 15 课 ◆｜Web 安全基线与 AI 特有风险 ｜**交付 M5**｜含 15 分钟小测

**目标句**：你能在教师提供的漏洞靶场里**分别验证每一层防护各自挡住了什么**，并核查自己项目的对应防线是否到位。

**合规声明**：所有攻防仅限课程提供的本地靶场；严禁对任何真实系统实施，须签署确认书。

- **前置卡**：第 14 课会话、Cookie 与 CSRF 基线；第 5 课模板转义；第 2 课 `textContent`
- **核心解释目标**：浏览器为什么会执行别人写的脚本，以及每一层防护各自挡住了什么

**实验设计（本版核心修正：同一漏洞基线的三组独立对照，不是累加式分步）**

靶场提供一个**存在存储型 XSS 的基线版本**，但保留已启用的 CSRF 检查。从**同一基线分别出发**做 A/B/C 三组独立实验，只改变各组指定的防护配置；每组恢复相同数据与登录态。目标写端点真实存在，当前用户拥有操作权限，正文及适用的版本条件合法。基线的正常页面脚本已外置并同源；载荷由服务端 HTML 模板输出，并已在基线中确认能够执行，避免把 DOM 插入方式或其他校验失败误当成 CSP/HttpOnly 的效果。

| 独立对照 | 只改什么 | 应观察到什么 | 不能据此推出什么 |
|---|---|---|---|
| A · 只加安全渲染 | 输出改为转义/白名单清洗 | 注入内容不再作为脚本执行——**根因修复** | — |
| B · 只加 `HttpOnly` | 只改会话 Cookie 属性，渲染仍不安全，CSRF 检查保持开启 | 脚本读不到会话 Cookie，但携带合法 CSRF 凭证的同源脚本仍能借登录会话操作；按下面 B1/B2 两次请求区分拒绝原因 | 不能说 XSS 已被消除，也不能说 CSRF 防护能够消除 XSS |
| C · 只加限定 CSP | 仅增加 `Content-Security-Policy: script-src 'self'`，正常页面脚本外置并同源 | 本样本的内联 `<script>` 与内联事件处理器均被阻止；本组不设置 `script-src-elem` / `script-src-attr`，也不启用 nonce/hash 或 inline 放行项 | 不能推出所有 XSS 都被消除；其他利用路径是否可行取决于策略与应用，不预设一定可绕过 |

**B 组内的两次请求对照（不是增加两套独立防护配置）**

| 小步 | 固定条件与唯一变化 | 观察与解释 |
|---|---|---|
| B1 | 对靶场中已存在的受保护 SSR 写端点发请求，登录、权限、正文均合法，唯独不提交同步器 token | 403 且核对 CSRF 拒绝原因，无业务写入；这次拒绝来自 CSRF，不来自 HttpOnly |
| B2 | 使用相同会话与等价初始数据，脚本从同源表单 DOM 读取 token 并按原接口契约提交，其余条件不变 | 写入成功并回读确认；浏览器自动携带会话 Cookie，脚本不必读到它。CSRF 防护不消除 XSS，因为已执行的同源脚本可能获取并提交 token |

> B1/B2 是教师提供脚本的引导观察，学生解释结果，不新增攻击代码编写任务。SPA 的固定自定义头方案另在下方核对：它不是必须从 DOM 读取的秘密 token，同源脚本可以设置它，不能混同这两种方案。
> 三组做完后**再合并成安全基线**，并说明：A 是根因修复，B 与 C 是纵深防御。

**CSRF 两种方案的成立条件（不可无条件互换）**

| 方案 | 适用 | 成立条件 |
|---|---|---|
| 同步器 token | **SSR 表单** | 服务端生成、随表单下发、提交时服务端校验并与会话绑定 |
| 自定义请求头 | **SPA 写请求** | **服务端必须强制校验约定的头，不允许其他内容类型或备用路径绕过**；CORS 只允许受信任的具体来源，不能包含攻击者来源。本课程主线采用反向代理同源，不开放跨源凭据；确需跨源时可对明确可信的具体来源开放凭据，不能使用通配来源或无校验地反射来源。仅在前端加一个头不构成防护 |

本项目同时保留 SSR 与 SPA，**两条都要有**。第 14 课模板已引入，本课负责解释原理并验证拒绝路径：**保持登录、权限、资源、正文及适用的版本条件合法，只移除对应 token 或自定义头**，核对 403、CSRF 拒绝原因与无业务写入。与一条合法请求作对照，不能只凭「请求被拒」断言防护有效。

**常用写法卡 #15**
清理 `|safe` 与 `dangerouslySetInnerHTML` / 富文本白名单清洗 / 全部查询参数化 / CSRF 两方案及其成立条件 / 安全响应头基线（最小可用 CSP、`X-Content-Type-Options`）/ 上传类型与文件名校验 / `pip-audit`、`npm audit` / 生产配置检查表。
→ 浏览器**不替你转义**的四个位置：HTML 文本、属性值、URL、JS 上下文。
→ **必须知道的边界**：**`HttpOnly` 只阻止脚本读取 Cookie，不消除 XSS**——注入脚本仍可借已登录会话发起操作；根因修复是安全渲染，Cookie 属性与 CSP 属于纵深防御。

### 第 16 课 ◆｜AI 服务集成与上线交付 ｜**交付 M6** + 课程收束

**目标句**：你能给应用加上流式 AI 摘要（含失败降级与中途断开处理），并把整个应用部署到一个可访问的地址。

- **前置卡**：第 5 课异步判据；第 10 课构建产物与同源判定；第 11–12 课闭包与状态快照；第 13 课深链接
- **核心解释目标**：长耗时请求的三种形态，各自把等待放在哪——同步 / 流式 / 后台任务
- **环境前提**：**部署平台账号、容器环境、预览地址在课前由教师统一就绪**，课堂不做首次注册与环境排错；主线通过反向代理让页面与 API 同源，跨源配置使用教师隔离示例比较

**本课补讲：最小函数式更新（回收闭包与状态快照）**
教师固定示例只启动一个异步读取循环，循环捕获某次 render 的 `text`，初值为 `""`，依次收到已解析的业务片段 `"A"`、`"B"`、`"C"`，期间不重启循环、不重置状态、不由其他代码写入文本。`setText(text + chunk)` 反复使用同一旧基线，最终为 `"C"`；`setText(prev => prev + chunk)` 按先前状态追加，最终为 `"ABC"`。**原因是读取了哪一次 render 的值，而非 chunk 到达太快**；每秒一个片段也不会改变原循环捕获的值。这是第 11 课事件处理函数、第 12 课 Effect 闭包的第三次回收；完整更新队列、批处理与并发渲染仍放参考层。

**流式失败处理（模板必须覆盖，学生要求解释失败分支）**

判据是**应用是否已发送 ASGI `http.response.start`**，不是是否构造了响应对象、生成器是否第一次 yield、浏览器是否已看到文字。常规 `StreamingResponse` 先发送启动事件，再迭代正文；即使还没有业务文本，也不能假定还能改成普通错误响应。协议服务器可能缓冲启动事件，发送该事件不等于字节已到浏览器；课程模板不能依赖这种缓冲补救。

| 时机 | 处理方式 | 不能承诺什么 |
|---|---|---|
| **响应尚未启动**（应用还未发送 `http.response.start`） | 返回错误状态码，或选择非流式降级 | 不能仅以「尚无首段文本」判断还在这个阶段 |
| **响应已启动、连接仍可写** | 尝试发送约定的流内错误事件；前端保留已收内容并标记不完整 | 应用不能重新选择 HTTP 状态码，也不能保证错误事件一定送达 |
| **连接已断开** | 清理上游资源；前端通过读取异常或无结束事件的连接结束识别不完整 | 不能承诺还能通知前端 |
| 正常结束与前端判定 | 只有收到**本次流的成功结束事件**且此前无流内错误，才标记完整；结束事件之前的 EOF、读取异常或超时均为不完整 | 「没收到错误事件」或普通 HTTP 200 都不等于流式结果完整 |
| 重试 | 已产生部分输出时**不自动重试**；用户明确重试时开启新一轮、替换旧内容，防止旧流继续写入，并计入总成本预算 | 不能把重试当作没有额外费用或副作用 |

> **教师模板责任**：为实现「响应启动前上游失败 → 降级可见」，须在启动下游响应之前，在有限超时内完成上游建连与首个业务内容片段预读；空流、超时或异常走普通错误或非流式降级。预读成功后启动响应，首段不得遗漏或重复，所有退出路径均清理上游资源。前端按媒体类型区分非流式降级与 SSE，并由教师提供的解析器处理事件边界；网络分包不等于业务片段。资源管理、预读与解析内部不要求学生从零实现；学生解释失败分支与完整性判据。

**常用写法卡 #16**
`httpx.AsyncClient` 调 LLM + 超时 + 有限重试 + 降级 / SSE 流式端点 + 前端流式渲染（模板，**要求解释失败分支**）/ **函数式更新累积流式文本** / **LLM 输出必须转义后再渲染** / 静态托管 + SPA fallback + API/SSR/探针分流 / **CORS**：同源定义、预检、白名单与凭据条件 / 单容器 Dockerfile + `docker compose up` / 迁移与发布的先后顺序 / 上线检查清单（安全 / 性能 / 日志 / 回滚）。
→ 出错通常在：无超时、无成本上限；前端直接持有 LLM 密钥；流式开始后仍试图用状态码表达失败。
→ **必须知道的边界**：**超时、断连等无法确认上游处理结果的故障，可能意味着结果未知**（可能已产生费用、可能已完成），不能无条件重试；明确的错误响应按其语义处理，不能把所有失败都称为未知。**LLM 输出是不可信数据。** 另外，**dev proxy 消失不等于生产一定跨源**——本课程主线用反向代理保持同源，确需跨源时才配置受信任的具体来源与凭据条件。

**关键观察点（先预测）**

### 3. 事务主路径（全课程唯一）

> **服务层业务用例入口拥有事务边界并显式提交；内部辅助函数与数据访问层只读写、不各自提交；端点只做 HTTP 翻译；依赖只提供资源与清理。**
> 第 7 课引入 Session 后沿用同一划分，**不得在成功响应发出后才提交**。其他提交位置的方案放参考层，不出现在主线示例中。

| 故障分类 | 处理与保证范围 |
|---|---|
| 已识别的业务约束冲突 | 仅将已知约束映射到批准的业务异常与 `code`，如标题唯一冲突按既有契约返回 409；422 仍按输入校验契约处理，不把任意数据库异常统一改成 409/422 |
| 基础设施故障 | 连接建立失败、驱动或数据库故障走服务器错误路径：未知错误为 500，已识别的暂时不可用可按契约为 503；不包装成业务冲突，数据结论取决于故障位置 |
| 提交结果未知 | 提交期间断连、超时或确认丢失，是需单独识别的基础设施故障；既不能断言已提交，也不能断言未提交。记录 request-id、操作类型、目标标识等必要核对信息，不记录密钥或敏感正文，不自动重试写入 |

**统一结论：成功响应晚于提交完成，但失败响应不意味着没有发生写入。** 清理连接或调用 rollback 也不能撤销已经确认提交的事务。

**M2/M3 教师验收脚本要求**：两组故障都在 HTTP 响应启动前、使用非自动提交事务。第一组在 SQL/flush 成功后、服务层 `commit()` 调用前抛错，回滚并用独立连接确认无本次写入；第二组在 `commit()` 确认成功返回后抛错，确认 500 但本次写入可见。真实提交组使用可丢弃的专用数据库与独立连接，不能用 savepoint 或测试结束时的外层回滚伪装提交结果。提交期间断网不由这两个开关模拟，不能推广出固定的数据结论。

## 十三、实施顺序与试讲验证

**落地顺序**
1. 写学生版《课程地图》与《每课一页》（含每课那一条边界 + 模板标注清单）。
2. 补《契约与迁移交接表》，特别是**第 14–15 课认证与 CSRF 引入后的回归变更清单**。
3. **核验两类关键模板**：
   - **事务模板**——沿用服务层业务用例入口显式提交，逐项同步第 4、7、8、9、14 课正文代码与测试说明；教师脚本注明提交前/后注入点与独立回读方式，答案卡区分业务冲突、基础设施故障与提交结果未知。
   - **流式模板**——核验响应启动前的有限超时首段预读与降级、启动后连接可写时的错误事件、成功结束事件与缺失时的不完整判定、已输出后不自动重试；脚本覆盖三条验收路径及错误事件未送达的断连变体，不能只靠正文生成器内部的 try/except 承诺修改状态码。
4. 改每节课的前 40 分钟结构：目标句 → 前置卡 → 正例构建 → 学生第一次独立决定（限定在实现方式/测试输入/情境判断范围内）。
5. 重写 lesson-10 ~ 13 底稿；第 12 课备妥固定 Query 工程、配置、缓存起点、操作序列与答案卡；第 16 课备妥固定读取循环和初始状态，不以真实网络分包频率证明闭包结论。
6. 第 15 课准备 A/B/C 三组配置与重置脚本，B1/B2 只作为 B 组内的请求对照；给出每组单一变化项、可证明与不可推出的结论，校准 CSP 指令回退与事件属性的 nonce/hash 边界。

**首轮试讲：第 3 课与第 11 课。** 各自起始工程、契约与教师答案核验完成后即可试讲，可与第 12、15、16 课配套材料修订并行。上面的模板、脚本和答案卡是**后续实施要求，不表示已实现或实测通过**；涉及它们的课次须在试讲前完成核验。

**观察指标（本版修订第一项）**

| 指标 | 记录方式 |
|---|---|
| ① **在不给完整答案的前提下，多少学生完成了指定小变式；各需要哪一级提示；能否解释结果** | 提示分三级：L1 指出方向（「看一下参数在哪一步被转换」）／L2 给出局部线索（「检查 `res.ok` 的位置」）／L3 给出可对照的片段。记录每人达成所需的最高提示级别与完成用时 |
| ② 关键观察点的预测正确率与**错因类型** | 按「概念未建立 / 条件读漏 / 推理断层」三类归档 |
| ③ 出口小题中「解释运行结果」一类的得分分布 | 与其他题型分开统计 |

据此决定是否继续减量。若 L3 提示比例偏高或完成用时显著超出预留时段，优先削减该课学生任务的范围，而不是压缩正例构建时间。
