# 二、正文

## 1.0 开场：建立三个坐标系

### 1.0.1 课程范式与能力分界
时长: 3min
要求: 这一段是整门课的定调，语气要直接，不要客套。核心是一句判断句——"你们不是不会让 AI 写代码，你们是不会审 AI 写的代码"——这句要单独立住，前后留白，让学生被扎一下。课程五步范式要一次性给完，因为后面 15 次课都是这个循环，学生越早知道节奏越安心。

内容:
你们的起点：已经用 AI 生成过能跑的 Web 页面和接口。
你们的困境：看不懂它生成的代码，因此也无法约束它去做更复杂的系统。
AI 时代全栈能力的分界线，从"能写出来"移到了"能判断对不对、能指出错在哪一层"。

本课程每次课的固定五步：
1. 解剖一段 AI 生成代码（能跑、看着专业、有隐藏缺陷）
2. 现场写代码，写到坑上就地讲原理
3. 用观察工具打开一处黑盒（调试器 / 日志 / DevTools / 执行计划 / 构建产物）
4. 沉淀判据表与跨栈对照卡
5. 课后按"规格 → 生成 → 审查 → 修复"闭环交作业

讲: 先说清你们现在在哪。你们不是零基础——你们都用 AI 写过能跑的东西。你们缺的也不是打字速度。
你们缺的是：AI 给你一百行代码，你没有任何依据判断这一百行是好是坏，更说不出它错在哪一层。
所以我把话说直白：这门课不教你怎么让 AI 写得更快，教你怎么审它、怎么约束它、怎么在它写歪的时候一眼看出歪在哪。
每次课都是同一套节奏：先拆一段 AI 代码，然后我现场写，写到坑上就停下来讲原理，
然后用工具打开一个黑盒给你看内部，最后给你一张判据表。十六次课，节奏一样，你们会习惯的。

### 1.0.2 请求链路图（空骨架）
时长: 3min
要求: 这是全课程的主图，第 16 次课之前每次课都要拿出来局部高亮。**首次出现时必须是"空的、带问号的"**——学生要先感受到"我不知道这里面有什么"，再在 16 次课里逐格填实。今天只点亮中间那一段，两侧问号必须保持问号，并明确说出它们各自在第几次课填。教师同时在黑板画同一张图，学生跟着画进作业。

内容:
一次请求的完整旅程（本课程的地图）：

浏览器 →〔DNS〕→〔CDN?〕→〔反向代理?〕→〔ASGI 服务器〕→〔中间件栈〕
→〔路由匹配〕→〔参数校验〕→〔依赖注入〕→〔路由函数〕→〔服务层〕→〔仓储层〕
→〔数据库?〕，旁挂〔缓存?〕〔队列?〕〔LLM?〕

本课实现：ASGI 服务器 → 中间件栈 → 路由 → 校验 → 依赖 → 路由函数 → 服务层 → 仓储层
本课不碰：左侧 DNS / CDN / 反向代理（第 16 次课）
          右侧数据库（第 5 次课）、缓存（第 16 次课）、队列与 LLM（第 15 次课）

图: 请求链路全景骨架。从左到右一条主链，方框串联；数据库、缓存、队列、LLM 作为旁挂节点。
    未实现的节点保留问号标记。本课覆盖的中段需要能被整体高亮，
    且**这张图后续每次课都要复用并高亮不同区段**，请做成可局部高亮的版本。

讲: 这张图你们要画进笔记，而且以后每节课我都会把它调出来，告诉你们今天在填哪一格。
现在它是空的，一堆问号，这很正常——你们对 Web 系统的认知现在就是这样，
只知道"我点一下，它就返回了"，中间发生了什么完全是黑箱。
今天我们填中间这一段：从服务器接住请求，到最后碰数据的那一层。
左边这三个问号，DNS、CDN、反向代理，第十六次课上线时填。
右边数据库第五次课填，缓存和队列、还有调大模型，第十五、十六次课填。
十六次课以后你回头看这张图，应该每一格都能说出"谁负责、它挂了会怎样、我怎么观察它"。
这就是这门课的验收标准。

## 1.1 AI 代码解剖台 #1

### 1.1.1 AI 生成代码走读
时长: 4min
要求: **高光页。** 代码必须先完整、干净地上屏一次，不带任何标红、不带任何批注，让学生先在心里承认"这看着挺正常，我也这么写过"。给足 15 秒安静阅读时间，然后才开始逐处点亮问题。顺序不能反——先标红再走读，反转的力量就没了。
      提示词原文要给出来，因为学生要意识到"这不是 AI 水平差，是我的提示词没给结构约束"。

内容:
提示词原文："用 FastAPI 写一个帖子的增删查接口，连 SQLite。"
输出：ai_generated_posts.py（完整代码上屏）
事实前提：这段代码能启动、能跑通、能和前端联调成功、Swagger 文档能打开。

上屏片段（完整上屏，约 45 行，见 snippets/lesson01/ai_generated_posts.py）:
```python
app = FastAPI()
OPENAI_API_KEY = "sk-proj-8Kd3nQ...真实密钥"
DB = "app.db"

@app.post("/getPosts")
def get_posts(page: int = 1):
    conn = sqlite3.connect(DB)
    cur = conn.cursor()
    cur.execute(f"select * from posts limit 20 offset {(page - 1) * 20}")
    return {"success": True, "data": cur.fetchall()}

@app.post("/createPost")
def create_post(p: PostIn):
    conn = sqlite3.connect(DB)
    try:
        conn.execute("insert into posts(title, body, author) values(?,?,?)",
                     (p.title, p.body, p.author))
        conn.commit()
        return {"success": True, "message": "创建成功"}
    except Exception as e:
        return {"success": False, "message": str(e)}

@app.post("/deletePost")
def delete_post(id: int):
    conn = sqlite3.connect(DB)
    conn.execute(f"delete from posts where id = {id}")
    conn.commit()
    return {"success": True}
```

讲: 这是我给 AI 的原话：用 FastAPI 写个帖子的增删查，连 SQLite。就这一句。
它给了我这段。你们先看十五秒，别急着找问题，就当是你自己写的。
（停顿）看完了吗？我先说三件事：这段代码能启动，能跑通，前端能联调，Swagger 也能打开。
从"能不能用"这个标准看，它是合格的。这也是为什么你们过去从来没觉得它有问题。
但它有九个缺陷，而且——这句话你们记住——**九个里没有一个是语法错误**。
AI 的语法能力比你们强，这一点不用怀疑。它弱的地方在于：
你没告诉它结构该怎么组织，它就替你随便决定了，而它的随便决定几乎总是错的。

### 1.1.2 三问法示范
时长: 3min
要求: 三问法是全课程 16 次解剖台的统一工具，第一次给要讲透。只挑三行做完整示范，其余快速带过——示范的目的是让学生学会这套动作，不是穷举缺陷。第二问"位于链路哪一层"必须回指 1.0.2 的链路图，让两者建立绑定。

内容:
面对任何一段 AI 代码，问三个问题：
① 这行在干什么？
② 它位于链路的哪一层？（回到 1.0.2 的图上指位置）
③ 缺陷是什么、后果是什么？

三行示范：

`@app.post("/getPosts")`
① 注册进路由表，只接受 POST
② 路由层
③ 读操作用 POST → 响应不可缓存、超时后客户端不敢重试、URL 不能分享、CDN 完全失效；
   URL 用动词而非资源，客户端无法推断同族接口

`return {"success": False, "message": str(e)}`
① 捕获所有异常，以 200 返回
② 路由层，但越界承担了"错误契约"的职责
③ 客户端 res.ok 永远为真 → 前端每个接口都要手写判断；
   监控和网关只看状态码 → 故障永久静默；
   str(e) 把数据库结构和文件路径直接送给客户端

`f"delete from posts where id = {id}"`
① 字符串拼接生成 SQL
② 数据访问层
③ SQL 注入。本例中 `id: int` 恰好挡住了，
   但同一手法一旦用在 keyword、order_by 上立刻可利用（第 14 次课现场拖库）

讲: 这套三问，你们以后每看一段 AI 代码都要走一遍，十六次课下来会变成本能。
第一问最简单，这行干什么。第二问最关键：它在我那张链路图的哪一格？
你说不出来，就说明你根本不知道这行代码在系统里的位置，那你怎么可能判断它对不对。
第三问是后果——注意我要的不是"这样不好"，是"这样具体会导致什么事发生"。
比如读操作用 POST，后果是什么？CDN 缓存全废、超时了你不敢重试、URL 发不了给同事。
这三条都是能被观测到的具体损失，不是风格问题。
最后这个拼 SQL，今天恰好被类型注解挡住了。但你注意"恰好"这个词——
它不是被设计挡住的，是运气好。第十四次课我们把同样的写法用在搜索关键词上，现场把数据库拖出来。

### 1.1.3 九条缺陷汇总
时长: 3min
要求: 这张表 9 行，超过 8 行，请注意处理。**只需高亮"本课修"那一列打勾的六条**，未打勾的三条一句话带过即可。表格的关键价值在最右列——每条缺陷都标出"哪次课修"，让学生看到整门课是有计划地在还这份技术债，而不是零散知识点。这一列不能省。

内容:

| # | 缺陷 | 所属层 | 后果 | 本课修 | 后续课 |
|---|---|---|---|---|---|
| 1 | 读操作用 POST、URL 用动词 | 路由 | 不可缓存 / 不可重试 / 语义不可推断 | ✅ | 第 8 课资源化 |
| 2 | 失败也返回 200 | 错误契约 | 故障静默、前端逻辑污染 | ✅ | 第 8 课 problem+json |
| 3 | `str(e)` 直接回传 | 错误契约 | 信息泄漏 | ✅ | 第 14 课 |
| 4 | 密钥硬编码 | 配置 | 泄漏、无法多环境部署 | ✅ | 第 16 课密钥管理 |
| 5 | 无响应模型，`select *` 返回裸元组 | 序列化 | 内部字段泄漏、前端只能按下标取值 | ✅ | 第 8 课契约 |
| 6 | 每个路由手建连接、不关闭 | 依赖管理 | 连接泄漏、无事务边界、无法测试替换 | 部分 | 第 3、6、7 课 |
| 7 | 业务规则/数据访问/HTTP 全挤一处 | 分层 | 无法复用、无法单测、改一处动全身 | ✅ | 贯穿全课 |
| 8 | 拼接 SQL | 数据访问 | 注入 | — | 第 5、14 课 |
| 9 | 无日志、无请求标识 | 可观测性 | 出问题无法定位 | ✅ | 第 16 课 |

讲: 九条，我今天当场修六条，剩下三条排在后面的课。
你们看最右边这一列——这门课不是一堆零散知识点，它是有计划地在还这段代码欠下的债。
第八课还契约的债，第十四课还安全的债，第十六课还部署和可观测性的债。
我再强调一遍那个共同点：这九条没有一条是语法错误。
所以"能跑"这个标准，从今天起在你们心里应该失效了。

### 1.2.2 入站契约与出站契约
时长: 4min
要求: **重点。** 核心是"入站和出站是两个不同的契约，不能共用一个模型"。两个类必须并排对比，学生要一眼看到字段差集：入站没有 id / created_at，出站没有内部字段。同时要立住一条判据边界——格式约束归 schema，业务规则归服务层——这条边界在 1.2.4 会被用到。

内容:
```python
class PostCreate(BaseModel):        # 入站：客户端允许提交什么
    title: str = Field(min_length=5, max_length=120)
    body: str = Field(min_length=10, max_length=5000)
    author: str = Field(min_length=1, max_length=40)

class PostOut(BaseModel):           # 出站：允许暴露给客户端什么
    model_config = ConfigDict(from_attributes=True)
    id: int
    title: str
    body: str
    author: str
    created_at: datetime
```

判据：
- 只看这一个请求就能判断的 → schema 层（长度、格式、类型、范围）
- 需要查系统当前状态才能判断的 → 服务层（标题是否重复、余额是否够）

图: 两个模型的字段差集示意。入站独有：无。出站独有：id、created_at。
    另标出"存储层还有 client_ip、moderation_note，两个模型都没有"。

讲: 注意这是两个类，不是一个。AI 特别喜欢生成一个 Post 模型两头用，那会出两种事故：
要么客户端能自己塞一个 id 进来伪造记录，要么你数据库里的内部字段全被吐出去。
入站为什么没有 id 和 created_at？因为这两个是服务端生成的，客户端不该也不能提供。
出站为什么要显式列字段？因为它是一道白名单，等下我会当场证明它的作用。
再看这些 Field 约束，标题至少五个字——这是格式约束。
但"标题不能和已有帖子重复"就不是格式约束了，因为它得去查数据库才知道。
这条线你们记住：只看这一个请求就能判断的放这里，得查系统状态的放服务层。这是今天第一条判据。

### 1.2.4 服务层：不认识 HTTP 的一层
时长: 6min
要求: **本段实操中最重要的知识点。** 必须让学生通读整个文件后意识到一件事：这里没有一处 import fastapi、没有一个 Request、没有一个状态码数字。这个"缺席"是要点，请用某种方式让"缺席"变得可见（例如列出该文件的 import 清单）。三种失败 → 三种领域异常的翻译链是板书内容。

内容:
```python
BANNED_WORDS = ("加微信", "代写", "刷单")

class PostService:
    def __init__(self, repo: InMemoryPostRepo) -> None:
        self.repo = repo

    def get_post(self, post_id: int) -> PostRecord:
        row = self.repo.get(post_id)
        if row is None:
            raise NotFoundError(f"帖子 {post_id} 不存在")
        return row

    def create_post(self, data: PostCreate, *, client_ip: str) -> PostRecord:
        hit = next((w for w in BANNED_WORDS if w in data.body or w in data.title), None)
        if hit:
            raise RuleViolation(f"内容包含违规词：{hit}")
        if self.repo.title_exists(data.title):
            raise ConflictError("已存在同标题的帖子")
        return self.repo.add(title=data.title, body=data.body,
                             author=data.author, client_ip=client_ip)
```

该文件的 import 清单（要点在于"没有什么"）：
```
from app.errors import ConflictError, NotFoundError, RuleViolation
from app.repositories.post_repo import InMemoryPostRepo, PostRecord
from app.schemas.post import PostCreate
——没有 fastapi，没有 Request，没有 Response，没有任何状态码
```

图（板书）: 翻译链三行并列——
    找不到 → NotFoundError → 404
    违规词 → RuleViolation → 422
    标题重复 → ConflictError → 409
    箭头第一段发生在服务层，第二段发生在错误处理器（1.3.1），服务层对第二段一无所知。

讲: 这个文件是今天最重要的一个文件，我要你们看它"没有什么"。
看 import：没有 fastapi，没有 Request，没有 Response，没有一个状态码数字。
这一层根本不知道自己在为 HTTP 服务。它为什么要这样？三个具体的好处：
第一，第四课我们做服务端渲染的表单页面，同一个 create_post 直接复用；
第十五课后台任务队列里，还是这个 create_post。它不认识 HTTP，所以谁都能调它。
第二，第八课写测试，我可以直接 PostService(repo=假仓储)，不启动 HTTP、不连数据库，毫秒级跑完全部业务规则。
如果这一层 import 了 Request，这件事就做不成了。
第三，你看这三种失败，我抛的是三个业务异常，不是三个状态码。
"这算 404 还是 409"是 HTTP 层的翻译问题，不是业务问题。所以翻译放在下一个文件里，统一一处。
最后回到刚才那条判据：违规词和标题查重为什么在这儿不在 Pydantic 里？
因为它们要知道系统里已经有什么数据。这就是"得查系统状态"的那一类。

### 1.2.5 依赖装配
时长: 2min
要求: 快讲。只需说清一件事：组装对象的职责被从服务层和路由层同时抽走了，这个专门的地方就是依赖注入的落点。lru_cache 单例是临时手段，必须声明它的有效期（第 6、7、16 课各会替换一次）。

内容:
```python
@lru_cache
def _shared_repo() -> InMemoryPostRepo:
    # 临时手段：进程内单例，让内存数据在多次请求间存活
    # 第 6 课改为「每请求一个数据库会话」；第 7 课在此定义事务边界
    return InMemoryPostRepo()

def get_post_service() -> PostService:
    return PostService(repo=_shared_repo())
```

讲: 注意"谁负责组装对象"这件事，被从两个地方同时抽走了。

那谁来组装？就这个文件。这就是依赖注入的落点，第三课整节课讲它。

第六课它变成每请求一个数据库会话，第七课在这里划事务边界，

### 1.2.6 路由层与出站白名单
时长: 4min
要求: **重点，含一个必须做的现场演示。** 演示动作：临时删掉 `response_model=PostOut` → 重新请求 → client_ip 和 moderation_note 出现在响应里 → 改回。这个演示把 1.1.3 的第 5 号缺陷变成学生亲眼所见的事故。演示前后的两份响应体必须并排对比。

内容:
路由函数只做四件事：声明契约 → 调服务 → 翻译成 HTTP → 返回。**业务判断零行。**

```python
router = APIRouter(prefix="/api/posts", tags=["posts"])

@router.get("", response_model=PostPage)
def list_posts(page: int = Query(1, ge=1),
               size: int = Query(20, ge=1, le=100),
               keyword: str | None = Query(None, min_length=2, max_length=40),
               svc: PostService = Depends(get_post_service)):
    items, total = svc.list_posts(page=page, size=size, keyword=keyword)
    return {"items": items, "meta": {"page": page, "size": size, "total": total}}

@router.post("", response_model=PostOut, status_code=201)
def create_post(payload: PostCreate, request: Request, response: Response,
                svc: PostService = Depends(get_post_service)):
    row = svc.create_post(payload, client_ip=request.client.host)
    response.headers["Location"] = f"/api/posts/{row.id}"
    return row
```

参数三种来源在签名里一目了然：路径参数 Path、查询参数 Query、请求体 Pydantic 模型。
校验规则声明在此，**没有一行 if**。

现场演示（出站白名单）:
有 response_model 时的响应体：
```json
{"id":1,"title":"...","body":"...","author":"lin","created_at":"2025-..."}
```
删掉 response_model 后的响应体：
```json
{"id":1,"title":"...","body":"...","author":"lin","created_at":"2025-...",
 "client_ip":"127.0.0.1","moderation_note":"auto-approved"}
```

讲: 路由函数只干四件事：声明契约、调服务、翻译成 HTTP、返回。你们数一下，业务判断几行？零行。
再回头看那段 AI 代码，它一个函数里干了六层的活。
参数从哪来，签名里写得清清楚楚：路径里的、查询串里的、请求体里的。
校验规则也在签名里，你们看，一行 if 都没有。
现在做个演示。我把 response_model 删掉，重新请求。
（运行）看到了吗？client_ip 出来了，moderation_note 也出来了。
这就是刚才那张缺陷表的第五条。response_model 是一道出站白名单，
你删掉它，等于把数据库表结构直接公开。第十三课如果这里漏的是密码哈希，那就是安全事故。
我改回去。以后你审 AI 代码，看到一个返回数据的端点没有 response_model，直接判不合格。

### 1.2.7 应用工厂
时长: 2min
要求: 快讲。只讲"为什么用工厂函数而不是模块级 app = FastAPI()"这一个问题，给三条理由。装配顺序（中间件 → 异常处理器 → 路由）本身也是内容，因为 1.4.4 的调用栈会印证这个顺序。

内容:
```python
def create_app() -> FastAPI:
    settings = get_settings()
    setup_logging(settings)
    app = FastAPI(
        title=settings.app_name, version=settings.version, debug=settings.debug,
        docs_url="/docs" if settings.env != "prod" else None,   # 生产不暴露文档
        openapi_url="/openapi.json" if settings.env != "prod" else None,
    )
    app.add_middleware(RequestContextMiddleware)

    app.include_router(health.router)
    app.include_router(posts.router)

app = create_app()
```

三条理由：
1. 测试里能用不同配置造多个互不干扰的 app（第 8 课立刻用到）
2. 装配顺序被显式写成一段可读流程，而不是散落在 import 副作用里
3. import 模块不再产生启动副作用

讲: 为什么不直接在模块顶上写 app = FastAPI()？三个理由。

二，你看这个函数体，装配顺序是明写出来的：先中间件，再异常处理器，再路由。
这个顺序不是随便的，等一下看调用栈的时候你们会看到它就长在栈里。
三，import 这个模块不会有副作用，不会一 import 就起服务。
这个模式在别的框架里也一样，Flask 叫 create_app，NestJS 叫 NestFactory.create，

### 1.3.1 领域异常与统一翻译
时长: 8min
要求: **重点。** 三件事要讲透：① 领域异常家族与 HTTP 状态码的映射只在这一处，加新错误类型不需要动任何路由；② 响应体形态是 problem+json，但**明确告诉学生这是简化版**，第 8 课补完（这个缺口是故意留的）；③ 兜底 handler 的边界——栈只进日志，绝不进响应体。
      与 1.1 的解剖台形成正面对撞：那边是每个路由自己拼错误体，这边是一处翻译全站统一。

内容:
```python
class AppError(Exception):          # 业务代码只抛这个家族，不碰 HTTP
    status_code, code, title = 500, "internal_error", "Internal Server Error"

class NotFoundError(AppError):   status_code, code, title = 404, "not_found", "Not Found"
class ConflictError(AppError):   status_code, code, title = 409, "conflict", "Conflict"
class RuleViolation(AppError):   status_code, code, title = 422, "rule_violation", "Unprocessable Entity"
class PermissionDenied(AppError): status_code, code, title = 403, "forbidden", "Forbidden"  # 第 14 课启用
```

统一响应体（简化版 problem+json，第 8 课补齐）：
```json
{"type": "/errors/not_found", "title": "Not Found", "status": 404,
 "detail": "帖子 999 不存在", "request_id": "3ab77c01e9d2"}
```

四个注册的处理器：
| 处理器 | 捕获 | 产出 |
|---|---|---|
| `AppError` | 业务异常 | 各自的 status_code + problem+json，日志 WARN |
| `RequestValidationError` | Pydantic 校验失败 | 422 + **字段级 errors 数组** |
| `StarletteHTTPException` | 框架抛的 HTTP 异常 | 对应状态码 + 统一体 |
| `Exception` | 一切未预料的 | 500，**栈只进日志**，响应体只给 detail 与 request_id |

兜底处理器的关键两行：
```python
log.exception("unhandled error path=%s", request.url.path)   # 栈 → 日志
content=_problem(500, "internal_error", "Internal Server Error", "服务器内部错误")  # 响应体不含栈
```

讲: 这个文件是把业务异常翻译成 HTTP 响应的唯一地方。
好处是什么？我以后要加一种新错误，比如第十四课的"没权限"，
只需要在这加一个子类，任何一个路由都不用改。
对比那段 AI 代码：五个接口能有五种错误格式，前端要写五套解析逻辑。
这个响应体的形状是有标准的，叫 problem+json。我今天给的是简化版，
故意留了缺口——第八课我们把它打磨成前端能真正依赖的契约，那时候你们才会体会到今天缺了什么。
重点看这个 request_id 进了响应体。这是给用户和客服用的：
用户截个图发给你，你拿这个 id 去日志里一搜，那次请求的全部日志立刻到手。这个动作五分钟后现场演示。
最后看兜底这个。任何我没想到的异常，栈只写日志，客户端只拿到一句"服务器内部错误"加一个 id。
对内详尽，对外克制。那段 AI 代码是 str(e) 直接回传，
攻击者能从里面读出你的文件路径、库版本，甚至表结构。

### 1.3.2 request-id 中间件
时长: 6min
要求: 这一节要顺带回答一个学生必然会问的问题——"为什么这段是中间件而不是别的"。给出四个条件同时成立的判定（全部请求 / 同时看到请求与响应 / 包住耗时 / 异常路径也执行），这个判定是 1.5.2 判据表的引子。ContextVar 只讲用途不展开原理（第 4 课并发模型时回收）。

内容:
```python
class RequestContextMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        rid = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
        token = request_id_var.set(rid)
        started = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            access_log.error("%s %s -> EXC %.1fms", request.method, request.url.path,
                             (time.perf_counter()-started)*1000)
            raise
        else:
            response.headers["X-Request-ID"] = rid
            access_log.info("%s %s -> %s %.1fms", request.method, request.url.path,
                            response.status_code, (time.perf_counter()-started)*1000)
            return response
        finally:
            request_id_var.reset(token)
```

为什么必须是中间件——四个条件同时成立：
1. 要对**全部**请求生效
2. 要**同时**看到请求与响应
3. 要包住耗时测量的首尾
4. 异常路径上也必须执行

设计细节：外部传入的 X-Request-ID 优先沿用 → 第 16 课 Nginx 在入口统一生成注入；
多服务时同一 id 串起跨服务链路，这就是分布式追踪的最小形态。

图: 中间件洋葱简图。请求进入穿过中间件到达路由函数，响应出来再穿回。
    标出"耗时测量的起点与终点都在中间件里"。（第 4 课出完整多层版本，本图为简版）

讲: 这段代码干三件事：给每个请求发一个 id，记一行访问日志，把 id 写回响应头。
为什么它必须是中间件？四个条件：要管所有请求；要同时摸到请求和响应；
要包住计时的头和尾；出异常了也得执行。四条同时成立，这就是中间件的定义域。
下半节课我给你们一张表，讲横切逻辑到底该放中间件、放依赖、放装饰器还是放服务层——
AI 在这件事上错得最多，它习惯把这些东西复制到每一个路由函数里。
再看这一行：如果请求头已经带了 X-Request-ID，我就沿用它，不重新生成。
为什么？第十六课上 Nginx，入口统一生成这个头。将来你有好几个服务，
同一个 id 能把跨服务的日志串成一条。这就是分布式追踪最简单的形态。
这个 ContextVar 你们先当成"每个请求各自一份的全局变量"，
第四课讲并发模型的时候我会回来说它在事件循环和线程池两种情况下为什么都成立。

## 1.4 打开黑盒：一次请求的四处对照追踪

> 说明给制作团队：1.4 是本课的核心演示段，全程双窗口同屏（日志 + 终端/浏览器）。
> 底稿给出的所有 `预期输出:` 都请做成兜底页面，重点是标注"哪几行要被指出来"。

### 1.4.1 四个观察点
时长: 2min
要求: 先立框架再演示，否则学生看不出章法。这张表的价值在"看不见什么"那一列——它解释了为什么需要四个观察点而不是一个。

内容:

| # | 观察点 | 工具 | 看得见 | 看不见 |
|---|---|---|---|---|
| 1 | 线路上的报文 | DevTools Network / `curl -v` | 方法、URL、头、状态码、体、耗时 | 服务内部发生了什么 |
| 2 | 应用访问日志 | 终端 | 每次请求的入口出口、状态、耗时 | 内部调用顺序 |
| 3 | 运行时调用栈 | VS Code 调试器 | 分层调用关系的**实证** | 只是断点那一瞬间 |
| 4 | 数据访问日志 | 终端（本课模拟，第 6 课为真 SQL） | 一次请求触发了几次查询 | 查询为何慢（第 5、6 课补执行计划） |

讲: 排查问题的时候你有四个地方可以看，各有各的盲区。
线路上的报文你能看到状态码和响应体，但服务内部发生了什么完全看不见。
访问日志能看到进出和耗时，但看不到内部调用了几层。
调用栈能看到分层关系，但它只是一瞬间的快照。
数据访问日志能看到一次请求打了几次数据库——这个数字以后会救你的命。
四个观察点合起来才是完整视野。接下来我用同一个 request-id 把这四处串起来。

### 1.4.2 追踪成功路径
时长: 5min
要求: **现场演示。** 关键教学动作是"指同一个值出现在四个地方"——响应头的 x-request-id 与三条日志的方括号里是同一串字符。这个视觉对应要做出来。
      第二个动作是让学生形成一个习惯：数一次请求打了几次数据库。这里是 2 次（查重 + 插入），第 6 课的 N+1 就靠这个习惯发现。

内容:
```bash
curl -i -X POST http://localhost:8000/api/posts \
  -H 'content-type: application/json' \
  -d '{"title":"ASGI 的三个参数怎么理解","body":"scope receive send 到底谁调用谁，看不懂","author":"lin"}'
```

预期输出（观察点 1）:
```
HTTP/1.1 201 Created
content-type: application/json
location: /api/posts/1
x-request-id: 9f2c1a4b7e30

{"id":1,"title":"ASGI 的三个参数怎么理解","body":"scope receive send 到底谁调用谁，看不懂",
 "author":"lin","created_at":"2025-..."}
```

预期输出（观察点 2 + 4，同一时刻的日志）:
```
INFO [9f2c1a4b7e30] app.repo    QUERY posts WHERE title='ASGI 的三个参数怎么理解' LIMIT 1
INFO [9f2c1a4b7e30] app.repo    INSERT posts -> id=1
INFO [9f2c1a4b7e30] app.access  POST /api/posts -> 201 3.7ms
```

要逐项指出的四处：
① 响应头 x-request-id 与三条日志方括号里是**同一个值**——这就是"串联"的全部含义
② 响应里**没有** client_ip / moderation_note——response_model 在起作用
③ 数据访问发生了 **2 次**（查重 + 插入）——请养成数这个数字的习惯
④ access 日志在**最后一条**——中间件是最外层，请求出去时它才收尾

补充演示（外部注入 id）:
```bash
curl -i -X POST ... -H 'X-Request-ID: demo-001' ...
```
→ 响应头与全部日志都变成 demo-001

讲: 发一个创建请求。看响应，201，Location 头告诉客户端新资源在哪，
还有这个 x-request-id。现在看日志这边——注意方括号里，同一串字符，三行日志都有。
这就是"串联"的意思：一个 id 把这次请求在系统里留下的所有痕迹绑在一起。
第二件事，响应里有 client_ip 吗？没有。response_model 挡住了。
第三件事，我要你们养成一个习惯：数这次请求打了几次数据库。这里是两次，一次查重一次插入。
这个习惯听起来无聊，但第六课你们会看到，一个看着正常的页面能打出一百零一次查询，
就是靠数这个数字发现的。
第四，注意 access 这行在最后。因为中间件在最外层，请求出去的时候它才收尾。
最后再演示一下，我在请求头里塞一个 demo-001 进去……你们看，整条链路都用了我给的这个 id。
第十六课 Nginx 就是这么干的。

### 1.4.3 追踪四条失败路径
时长: 5min
要求: **现场演示，四个 case 节奏要快。** 每个 case 的教学落点各不相同，不要平铺：
      404 的落点是"日志的三行就是链路的三层"；
      422 的落点是"日志里没有任何 repo 行，请求根本没进服务层"；
      409 的落点是"422 与 409 的分界"（这条 AI 几乎从不主动区分，是重点）；
      500 的落点是"栈只在服务端"。
      422 与 409 建议并排对比，因为它们的区分是本课判据的核心之一。

内容:

**(a) 404 — 服务层抛的领域异常**
```
GET /api/posts/999  →  404 application/problem+json
{"type":"/errors/not_found","title":"Not Found","status":404,
 "detail":"帖子 999 不存在","request_id":"3ab77c01e9d2"}
```
```
INFO [3ab77c01e9d2] app.repo    QUERY posts WHERE id=999
WARN [3ab77c01e9d2] app.error   AppError code=not_found path=/api/posts/999
INFO [3ab77c01e9d2] app.access  GET /api/posts/999 -> 404 1.2ms
```
落点：这三行日志**就是链路的三层**——仓储 → 错误翻译 → 中间件收尾。

**(b) 422 — 校验层拦下，根本没进服务层**
```
POST /api/posts  {"title":"短","body":"太短","author":""}  →  422
{"status":422, "detail":"请求参数校验失败",
 "errors":[{"field":"title","msg":"String should have at least 5 characters"},
           {"field":"body","msg":"String should have at least 10 characters"},
           {"field":"author","msg":"String should have at least 1 character"}]}
```
落点：日志里**没有一行 app.repo**。无效请求在最外层被挡回，零次数据访问。
      errors 是**字段级**的 → 第 10 课前端逐字段映射到输入框下方。

**(c) 409 — 业务规则冲突（重复标题再发一次）**
```
POST /api/posts  → 409
{"type":"/errors/conflict","status":409,"detail":"已存在同标题的帖子"}
```
落点：**422 与 409 的分界**——
      422 = 你给的东西本身不合规
      409 = 你给的东西没问题，但与系统当前状态冲突
      前端处理完全不同：422 高亮字段，409 提示换标题。

**(d) 500 — 临时在服务层插入 `1 / 0`**
```
响应： {"status":500,"detail":"服务器内部错误","request_id":"7c19..."}
日志： ERROR [7c19...] app.error  unhandled error path=/api/posts/1
       Traceback (most recent call last):
         File "app/services/post_service.py", line 18, in get_post
           1 / 0
       ZeroDivisionError: division by zero
```
落点：客户端拿到的是干净的 500 加一个 id，栈只在服务端。
      排障路径：用户报 id → 服务端 grep id → 直达栈。

讲: 四种失败，快过一遍。
先看 404。注意日志这三行——仓储、错误翻译、中间件收尾——**这三行就是链路的三层**。
日志顺序等于分层顺序，以后你看日志就是在看架构。
再看 422，我提交一个太短的标题。注意日志里有 app.repo 吗？一行都没有。
请求在最外层就被挡回来了，一次数据库都没碰。这就是把格式校验放最外层的价值：无效请求消耗最小。
还要注意 errors 是字段级的，第十课前端就靠这个把错误显示到对应输入框下面。
第三个最重要。我拿刚才成功创建过的标题再发一次，得到 409，不是 422。
区别在哪？422 是"你给的东西本身不合规"，409 是"你给的东西没问题，但跟系统现在的状态冲突"。
前端处理完全不同：422 要高亮出错的字段，409 要提示你换个标题。
这个区分 AI 几乎从来不做，它倾向于一律返回 400。你们审代码时重点看这里。
最后我故意在服务层插一个除零。客户端拿到什么？一句"服务器内部错误"加一个 id，干净。
栈在哪？只在我的日志里。对比 AI 那个 str(e)，那是把文件路径和库版本白送给攻击者。
用户截图报这个 id，我 grep 一下直接看到栈——这条排障路径，第十六课的定位四步法就从这里开始。

### 1.4.4 调用栈 = 分层图
时长: 6min
要求: **本课高光页。** 制作要点：
      左侧是调用栈（栈底在上、栈顶在下，与调试器一致），右侧是 1.0.2 链路图与 1.5.1 分层图的对应位置。
      **必须逐帧点亮、左右同步对位**，不能一次全给。教师会一帧一帧念下来，同时在黑板的分层图上指位置。
      这一页的目的是让"分层"从概念变成学生能用调试器指出来的实体，所以对位关系的清晰度高于一切。
      三个附带要点（中间件的位置、校验发生在路由函数之前、scope 是个字典）分别是第 4、3、3 课的引子，要点到但不展开。

内容:
在 `PostService.get_post` 的 `if row is None:` 处打断点，用 Swagger UI 发起 `GET /api/posts/1`。

调用栈（栈底 → 栈顶，已删无关帧）：
```
uvicorn ... RequestResponseCycle.run_asgi          ← ASGI 服务器
  └ FastAPI.__call__
     └ ServerErrorMiddleware.__call__               ← 兜底 500 在最外层包着
        └ RequestContextMiddleware.dispatch         ← 我们写的中间件（1.3.2）
           └ ExceptionMiddleware.__call__           ← 异常处理器在这里生效（1.3.1）
              └ starlette.routing.Route.handle      ← 路由匹配的结果
                 └ fastapi.routing.get_request_handler   ← 校验与序列化在此发生
                    └ run_endpoint_function
                       └ app.routers.posts.get_post      ← 路由函数（1.2.6）
                          └ app.services.post_service.get_post  ← 断点在此（1.2.4）
                             （下一步进入 repositories.post_repo.get）
```

四个要讲的点：
1. **黑板上的分层图不是隐喻，它就是运行时的栈。** 以后任何"这段代码在哪一层"的疑问，打个断点看栈即可
2. **中间件的位置**：ServerErrorMiddleware 在最外，我们的中间件在中间，ExceptionMiddleware 在内
   → 这解释了为什么异常处理器返回的响应仍会经过我们的中间件、因此仍带 X-Request-ID（第 4 课系统讲穿越顺序）
3. **校验发生在路由函数之前**：栈里 `get_request_handler` 这一帧就是校验执行处，
   所以路由函数拿到的 payload 已是合法对象（第 3 课打开这一帧）
4. Variables 面板里的 `request.scope` 是一个字典，装着 method / path / headers / client
   → "你拿到的 Request 对象，本质是这个字典的包装"（第 3 课展开 ASGI 三元组）

图: 左侧调用栈栈帧列表，右侧分层图。两侧逐帧对位点亮。这是本课高光页，
    对位关系的准确与清晰优先于一切装饰。

讲: 好，现在是今天最重要的六分钟。我在服务层打个断点，从 Swagger 发一个请求。
（命中）看调用栈。我从最下面往上念，你们对着黑板上那张分层图跟。
最外面是 uvicorn，ASGI 服务器，它接住了 TCP 上的字节。
往里，FastAPI 本体。再往里，这个 ServerErrorMiddleware——就是我们那个兜底 500，它在最外层包着。
再往里，RequestContextMiddleware，这是我们自己写的，发 id、记日志的那个。
再往里 ExceptionMiddleware，我们注册的那些异常处理器在这一层生效。
然后是路由匹配，然后——注意这一帧，get_request_handler，校验和序列化就发生在这儿。
所以我的路由函数拿到的 payload 已经是合法的了，我不用写 if。
再往里是路由函数，最后是服务层，断点在这儿。下一步就该进仓储了。
我要你们记住这一刻：**我讲的分层不是概念，不是目录洁癖，它就是运行时的这一串栈帧。**
以后任何时候你搞不清一段代码在哪一层，打个断点看栈，一目了然。
顺带三件事。一，看中间件的顺序，我们的中间件在异常处理器外面——
所以异常处理器返回的响应还会再穿过我们的中间件，所以 404 的响应里也有 request-id。第四课细讲。
二，校验在路由函数之前发生，第三课我们进这一帧里面看它怎么干的。
三，看变量面板里这个 request.scope，它就是个字典，装着 method、path、headers。
你以为 Request 是个很复杂的对象？它本质就是这个字典的包装。第三课我们把它拆开。

## 1.5 就地原理：四组判据

### 1.5.1 分层架构与依赖方向
时长: 6min
要求: **重点。** 不要讲"高内聚低耦合"这类空话，只讲三个可验证的收益，且每个收益都要指出"第几次课兑现"。
      表格 4 行不长，但最后一列"违反后的典型症状"是重点——学生要靠症状识别问题，而不是靠记规则。
      结尾的两条 grep 命令是学生作业的自查工具，要清楚上屏。

内容:
依赖箭头一律指向内层。

| 层 | 职责 | 允许 import | 禁止 import | 违反后的典型症状 |
|---|---|---|---|---|
| 路由 `routers/` | 声明契约、翻译 HTTP、调服务 | schemas、services、deps | repositories、直接 SQL | 业务逻辑无法被表单页/后台任务/测试复用 |
| 服务 `services/` | 业务规则、编排、事务边界 | schemas、repositories、errors | fastapi、Request、状态码 | 规则与 HTTP 绑死，单测必须起 HTTP 客户端 |
| 仓储 `repositories/` | 数据存取、查询构造 | 记录/模型类型 | services、routers | 换库要改遍全项目 |
| 契约 `schemas/` | 入站/出站数据形状与格式约束 | 无 | 任何业务与存储 | 存储字段泄漏、只读字段可被伪造 |

三个可验证的收益：
1. **可替换** — 第 6 课把 InMemoryPostRepo 换成 SQLAlchemy，services 与 routers 一行不改
2. **可测试** — 第 8 课 `PostService(repo=FakeRepo())` 毫秒级测完业务规则，不起 HTTP、不连库
3. **可定位** — 出问题能二分：access 日志确认是否慢在服务内 → repo 日志确认是否慢在数据访问
   （第 16 课定位四步法中"二分"的落点）

自查命令：
```bash
grep -rn "from app.repositories" app/routers/   # 应当无输出
grep -rn "fastapi\|starlette" app/services/     # 应当无输出
```

一句话判据：**写每段代码前问两个问题——这段代码需要知道 HTTP 吗？需要知道数据库吗？**
两个答案决定它该放哪一层。

图: 四层依赖方向图，箭头一律指向内层。标出被禁止的反向箭头（叉掉）。

讲: 分层的理由，我不跟你们说什么高内聚低耦合，那是空话。我说三个能验证的。
第一，可替换。第六课我把内存仓储换成真数据库，服务层和路由层一行都不改。
这是我今天当着你们做的承诺，第六课兑现，你们记着。
第二，可测试。第八课我直接 PostService(假仓储)，不起 HTTP、不连数据库，
毫秒级把所有业务规则测完。但前提是服务层不能 import Request——一旦 import 了，这事就废了。
第三，可定位。出问题的时候能二分：先看 access 日志，慢在服务内吗？
再看 repo 日志，慢在数据访问吗？一层层收缩。第十六课的定位四步法就靠这个。
最右边这一列你们重点看，是症状。你们以后不会记规则，你们会靠症状认问题。
"这个业务逻辑我复用不了"——那就是路由层塞了业务判断。
"我测这个规则得先起个 HTTP 服务"——那就是服务层 import 了 fastapi。
最后给两条自查命令，写完作业跑一下，有输出就是违反了。
还有一条判据，比什么都好用：写每段代码前问两句——它需要知道 HTTP 吗？它需要知道数据库吗？
两个答案就把位置定了。

### 1.5.2 横切逻辑的四个落点
时长: 5min
要求: 先给现象再给判据。现象是：AI 生成的代码里，鉴权、日志、限流、事务往往被复制进每一个路由函数。
      **要替 AI 说句公道话**——它是按"一个端点一段代码"的粒度生成的，看不到你项目已有的横切设施。这个解释很重要，它把结论导向"所以你必须在提示词里指定落点"，而不是"AI 很笨"。
      最容易混的是中间件与依赖的区分，判据要单独立出来。

内容:
现象：AI 生成的代码里，鉴权、日志、限流、事务常被复制进每一个路由函数。
原因：AI 按"一个端点一段代码"的粒度生成，看不到你项目里已有的横切设施。
结论：**你必须在提示词里明确指定落点。**

| 落点 | 判据 | 本课示例 | 后续课示例 |
|---|---|---|---|
| **中间件** | 对**全部**请求生效 + **同时**看到请求与响应 + 异常路径也执行 | request-id、访问日志、耗时 | CORS（第 11）、安全头（第 14、16） |
| **依赖（DI）** | 需**参数化** / 只对**部分**路由生效 / 结果要**作为值**传给业务代码 | 分页参数、get_post_service | 当前用户（第 13）、对象级授权（第 14）、DB 会话（第 6） |
| **装饰器** | 与框架请求对象无关的纯函数增强 | — | 重试与退避（第 15）、缓存（第 16） |
| **服务层内部** | 属于**业务规则**，不是技术设施 | 违规词、标题查重 | 事务边界（第 7）、审计记录（第 14） |

中间件 vs 依赖的关键区分：
**中间件不能把结果作为参数交给路由函数**（只能改请求/响应对象），**依赖可以**。
→ 所以"当前登录用户"必须是依赖（第 13 课会踩这一步）
→ "给所有响应加一个头"必须是中间件

图（板书）: 判据分叉图。三个问题依次分叉：要不要对全部请求生效？
    要不要把结果传给业务代码？是技术设施还是业务规则？叶子节点对应四个落点。

讲: 你们看 AI 生成的代码，会发现鉴权、日志这些东西被复制到每一个函数里，一模一样十遍。
这里我要替 AI 说句公道话：它是按"一个端点一段代码"的粒度在生成的，
它看不见你项目里已经有的中间件、已经有的依赖。所以这不是它笨，是你没告诉它。
结论就是：**你必须在提示词里指定落点。** 下课前那份提示词骨架里会有这条。
这张表最容易混的是前两行，中间件和依赖。判据是一句话：
中间件没法把结果作为参数交给你的路由函数，它只能改请求和响应对象；依赖可以。
所以"当前登录用户"这种东西，必须是依赖，因为你要在函数里用它。第十三课我们会实际踩这一脚。
反过来"给所有响应加一个安全头"，必须是中间件，因为它跟业务函数没关系。
最后一行也重要：违规词检查、标题查重，这些是业务规则，不是技术设施，所以在服务层里面，不在这三个落点上。

### 1.5.3 配置外置的三条原则
时长: 4min
要求: 快讲。三条 12-Factor 原则各配一条"不落实的后果"，后果比原则重要。
      结尾两条实践判据要留住，特别是"危险开关的默认值必须在安全的那一侧"——这条第 14 课会回收（AI 生成的配置类经常给 debug=True、allow_origins=["*"]）。

内容:

| 原则 | 本课落实 | 不落实的后果 |
|---|---|---|
| 配置存于环境（Factor III） | Settings 从环境/.env 读；.env 进 gitignore；只提交 .env.example | 密钥进 Git 历史（删不掉，只能轮换）；同一份代码无法多环境部署 |
| 一份代码库多份部署（Factor I/X） | env=dev/prod 切换 /docs 开关与日志级别 | 出现"生产版代码"与"开发版代码"两份分叉，行为差异不可控 |
| 日志作为事件流（Factor XI） | 全部日志写 stdout，不写文件、不切割 | 容器化后日志无法被平台采集（第 16 课直接受益） |

两条实践判据：
1. **启动时校验，缺配置即崩** — 配置错误必须在部署那一刻暴露
2. **危险开关的默认值必须在安全的那一侧** — `debug: bool = False` 而不是 True

讲: 三条，快过。
第一条，配置放环境变量，.env 不提交。为什么？密钥一旦进过 Git 历史，你删不掉，只能去吊销重发。
第二条，一份代码多份部署。反面是什么？项目里出现"生产版"和"开发版"两份代码，
然后某天生产上出了个开发环境复现不了的 bug，你查三天。
第三条，日志写标准输出，别自己写文件、别自己切割。第十六课容器化的时候你就明白了——
容器平台就是从 stdout 收日志的，你写文件它收不到。
最后两条判据。缺配置就崩，我开头演示过了。
还有一条：危险开关的默认值必须在安全那一侧。debug 默认 False，不是 True。
AI 生成配置类特别爱给 debug=True、CORS 给个星号全放开，部署上去直接就是漏洞。第十四课复现给你们看。

### 1.5.4 HTTP 方法性质与状态码判据
时长: 5min
要求: **重点，表格为主，是本课要沉淀进手册的核心资产。**
      方法性质矩阵 6 行，重点在"幂等"这一列，因为它是"可重试"的前提，后续第 8、16 课都要回收。请高亮 GET 与 POST 两行的对比。
      状态码判据表 12 行，超长。**只需高亮容易错的四组**：201 vs 200、401 vs 403、400 vs 422、409 vs 412。其余整屏上、不逐行念，学生课后抄。
      结尾必须回扣 1.1 的解剖台：那个 POST /getPosts 一次违反四条。这个闭环是本段的收尾力量。

内容:

**方法性质矩阵**

| 方法 | 安全（不改状态） | 幂等（重复执行结果相同） | 可缓存 | 典型用途 |
|---|---|---|---|---|
| GET | ✅ | ✅ | ✅ | 读取资源 |
| HEAD | ✅ | ✅ | ✅ | 只取头 |
| PUT | ❌ | ✅ | ❌ | 整体替换 |
| DELETE | ❌ | ✅ | ❌ | 删除 |
| POST | ❌ | ❌ | 特殊条件下可 | 创建、非幂等动作 |
| PATCH | ❌ | ❌（除非精心设计） | ❌ | 局部更新 |

幂等的价值是**可重试**：网络超时后客户端不知道服务端是否已处理。
GET/PUT/DELETE 可以直接重发；POST 不行——重发就是重复创建。
→ 第 8 课的 Idempotency-Key 就是为 POST 人工补上这个性质。

**状态码判据表**（只高亮打★的四组）

| 场景 | 用 | 不用 | 理由 |
|---|---|---|---|
| ★创建成功 | **201** + Location | 200 | 让客户端知道新资源在哪 |
| 更新/删除成功无返回体 | 204 | 200 + 空体 | 语义明确，省一次解析 |
| ★未登录（无凭证或凭证无效） | **401** | 403 | 401 = "你是谁"，应带 WWW-Authenticate |
| ★已登录但无权限 | **403** | 401 | 403 = "我知道你是谁，但不许" |
| 已登录无权限且不想暴露资源存在 | 404 | 403 | 防资源枚举（第 14 课） |
| ★请求语法/协议错误（JSON 坏了） | **400** | 422 | 400 = 我读不懂 |
| ★语法正确但字段不合规 | **422** | 400 | 422 = 我读懂了但不接受 |
| ★与当前状态冲突（标题重复、余额不足） | **409** | 400/422 | 冲突不是格式问题 |
| 带 If-Match 的乐观并发失败 | 412 | 409 | 前置条件失败（第 11 课） |
| 请求过多 | 429 + Retry-After | 400 | 客户端可据此退避 |
| 服务端 bug | 500（体内不含栈） | 200 | 监控与网关依赖状态码 |
| 依赖的下游不可用 | 502/503/504 | 500 | 区分"我坏了"与"我依赖的坏了"（第 15 课） |

**当堂对表纠错**（用今天写的端点）

| 端点 | 方法 / 状态码 | 符合矩阵？ |
|---|---|---|
| GET /api/posts | GET / 200 | ✅ 安全、幂等、可缓存（第 16 课加缓存头） |
| GET /api/posts/{id} | GET / 200 或 404 | ✅ |
| POST /api/posts | POST / 201 + Location | ✅ 但**不幂等** → 网络重试会重复发帖（第 8 课修） |
| GET /healthz | GET / 200 | ✅ |

回扣解剖台：`POST /getPosts` 一次违反四条 ——
方法性质（读用 POST，丧失安全/幂等/可缓存）、URL 语义（动词而非资源）、
状态码（失败也 200）、响应契约（select * 返回裸元组）。

讲: 这张方法性质表你们抄下来，后面好几节课都要回来看。
重点看"幂等"这一列。幂等是什么意思？同一个请求发一遍和发十遍，结果一样。
它的价值是什么？可重试。你发个请求超时了，你不知道服务端到底处理了没有。
GET、PUT、DELETE 你可以直接重发，无所谓。POST 不行——重发就是重复创建一份。
所以第八课我们要给 POST 人工补上这个性质，用一个叫 Idempotency-Key 的东西。
状态码这张表十二行，我只讲带星的四组，剩下的你们课后抄。
401 和 403：401 是"你是谁"，403 是"我知道你是谁但不许你干这个"。这两个 AI 经常混。
400 和 422：400 是我读不懂你的请求，JSON 都是坏的；422 是我读懂了但你的字段不合规。
409 最重要，就是刚才演示的：你给的东西没问题，是跟系统现在的状态冲突了。
现在拿我们今天写的端点对一遍表。GET 列表，安全幂等可缓存，合格。
POST 创建，201 加 Location，合格，但注意——它不幂等，网络一重试就重复发帖。第八课修。
最后回到开场那段 AI 代码。POST /getPosts，一次违反四条：
方法性质错、URL 语义错、状态码错、响应契约错。
你们记住这句话：**AI 生成 REST 接口最常错的就是方法和状态码**，
因为这部分靠语义判断，不靠语法正确，而它拿不到你的业务语义。这就是你必须审它的地方。

### 1.6.2 本课评审清单
时长: 1min
要求: 快讲，整屏上。这是学生审 AI 代码与自查作业的工具，五组共 18 条。只需读出每组的组名和最狠的那一条，其余课后用。

内容:

**分层与结构**
- 路由函数里是否出现业务判断（判条件、算价格、查重）？
- services/ 里是否 import 了 fastapi / Request / 状态码？
- routers/ 里是否直接 import repositories 或写 SQL？
- 数据库/外部客户端是否在路由函数内部手工创建？

**契约**
- 入站与出站模型是否分开？入站是否含 id、created_at 等客户端不该提供的字段？
- 每个返回数据的端点是否有 response_model？
- 是否存在把存储记录/ORM 对象直接返回的情况？

**HTTP 语义**
- 读操作是否全为 GET？URL 里是否出现动词？
- 创建是否 201 + Location？无返回体的更新/删除是否 204？
- 401/403、400/422、409 是否符合判据表？
- 是否存在"失败也返回 200"？

**错误与可观测性**
- 是否有统一错误处理器，还是每个路由自己拼错误体？
- 异常栈是否可能进入响应体？
- 是否有请求标识贯通响应头与日志？
- 一次请求打了几次数据访问？是否有意料之外的次数？

**配置**
- 是否有硬编码的密钥、URL、路径、魔法数字？
- .env 是否被忽略提交？是否提供 .env.example？
- debug、CORS 等危险开关的默认值是否安全？

讲: 十八条，五组，你们照着这个审 AI 的代码，也照着这个自查作业。
每组我念最狠的一条。分层组：路由函数里有业务判断吗？契约组：返回数据的端点有 response_model 吗？
语义组：有没有"失败也返回 200"？可观测组：一次请求打了几次数据库、有没有超出你预期？
配置组：有硬编码的密钥吗？
这五条命中任何一条，你就有充分理由把 AI 的输出打回去重写。

### 1.6.3 提示词约束骨架
时长: 1min
要求: 快讲。这份骨架是本课最实用的产出物，后续每课扩充一段。要点是让学生看到——它不是"请写得好一点"这种废话，而是把今天所有判据翻译成了可验收的约束。最后那段"交付要求"要特别指出，它是让 AI 自我暴露简化处的手段。

内容:
```
【项目结构约束】
按 routers / schemas / services / repositories / deps / config 分层。
依赖方向：routers → services → repositories；
services 不得 import fastapi、Request 或任何 HTTP 状态码；
routers 不得 import repositories、不得直接写 SQL。

【契约约束】
入站与出站使用不同的 Pydantic 模型；每个端点必须声明 response_model；
不得返回存储层记录或 ORM 对象；
入站模型不得包含 id、created_at 等服务端生成字段。

【HTTP 语义约束】
读操作用 GET，URL 使用名词复数资源路径，不得出现动词；
创建返回 201 并设置 Location；无返回体的更新/删除返回 204；
未认证 401、无权限 403、格式不合规 422、状态冲突 409；
禁止"失败也返回 200"。

【错误与配置约束】
所有错误经统一异常处理器输出 application/problem+json，
字段为 type/title/status/detail/request_id；异常栈只写日志不入响应体；
所有配置项经 pydantic-settings 从环境读取，不得硬编码密钥；
关键配置无默认值，缺失时启动即失败。

【交付要求】
在回答末尾列出：① 你做的结构决策清单；② 你未实现或简化的部分；
③ 你认为存在风险的地方。不要输出与上述约束冲突的代码。
```

讲: 这是今天最实用的东西，你们直接拿去用。
注意它长什么样：不是"请写得规范一点"这种废话，是把今天每一条判据翻译成了可以验收的约束。
每一条我都能拿去检查它的输出，能判对错。这才叫约束。
最后这段"交付要求"你们别漏。让它自己列出简化了什么、哪里有风险——
这一段能省你一半的审查时间，因为它会主动承认自己偷的懒。
以后每节课我都往这份骨架里加一段，十六课下来你们会有一份很厚的东西。
