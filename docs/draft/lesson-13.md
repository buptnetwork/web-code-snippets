## 一、开场：默认选项几乎总是错的

**约 4 分钟。**

### 1.1 一个数字

讲：

> 打开你们上次交的作业，数一下里面有多少个 `useState`。
>
> 我数了几份，**平均 14 个，最多的 31 个**。
>
> 然后我问一个问题：**这 14 个里面，有几个你认真想过"它该放在这里吗"？**

**封面级素材**：

> **`useState` 是默认选项。**
>
> **你不需要理由就能用它——这正是问题所在。**
>
> 一个状态放进 `useState`，你不需要做任何决定。
> 一个状态放进 URL、放进 Context、交给 query 层，**你都要做一个决定**。
>
> **而"不做决定"不是中立的，它是一个决定——通常是错的那个。**

### 1.2 放错的代价

**醒目页**：

| 状态放错了地方 | 用户看到的 |
|---|---|
| 筛选条件放 `useState` | **刷新一下，筛选全没了** |
| 筛选条件放 `useState` | **链接发给同事，他看到的是另一个页面** |
| 服务端数据放 Context | **改一个字段，半个页面重渲染** |
| 服务端数据放全局 store | **两个页面显示不同的数据，你不知道哪个对** |
| 深层组件要的状态放最外层 | **五层 props 传递，加一个字段改六个文件** |
| **权限状态只放前端** | **绕过去一行命令的事** |

> 前五行是工程问题。**最后一行是安全问题。**
>
> 今天会把六行全部演示一遍。

### 1.3 本次课要回答的问题

- 一个状态该放哪？有没有可以照着走的判断顺序？
- 为什么"能算出来就不要存"这条我们已经说了三次，还是会犯？
- 嵌套路由是什么？`lazy` 怎么和第 10 次课的代码分割接上？
- Context 到底解决什么问题？它的代价有多大？
- `useReducer` 什么时候比 `useState` 好？
- **第 5 次课那个 Jinja2 页面和今天的 SPA，到底哪个更好？**
- **AI 写的"权限控制"，为什么比它不写还危险？**

### 演示二：切个主题，整页重渲染（**用上节课的工具**）

打开 React DevTools → highlight updates。

**点一下"深色模式"开关。**

```
整个页面全部闪蓝框——包括 1000 行的表格。
```

> 主题跟表格有什么关系？**没有关系。**
>
> 但它们在同一个 Context 里。

**再用第 11 次课造的 `renderSpy` 量一下**：

```
切换主题：
  QuestionRow 渲染次数：1000
  FilterPanel 渲染次数：1
  SearchBar  渲染次数：1
```

> 一次主题切换，**1000 次无谓渲染**。
>
> 原因有两层，**两层都要讲**：
>
> **第一层：Context 的语义就是全量通知。**
>
> ```
> context value 变了 → 所有 useContext 的组件重渲染
> ```
>
> 它**不做字段级的订阅**。你读了 `state.theme`，但只要 `state` 这个对象变了，你就会被通知。
>
> **第二层：`value={{ state, setState }}` 每次都是新对象。**
>
> ```tsx
> <AppContext.Provider value={{ state, setState }}>
> ```
>
> **回收第 11 次课、第 12 次课：这是引用判等的第四次出现。**
>
> | 场景 | 每次新建的东西 | 后果 | 哪次课 |
> |---|---|---|---|
> | `memo` 失效 | 箭头函数 props | 白渲染 1000 次 | 第 11 次课 |
> | effect 无限循环 | 依赖数组里的对象 | **无限请求** | 第 12 次课 |
> | **Context 全量通知** | **`value` 对象字面量** | **全量重渲染** | **今天** |
>
> **同一条规则，第四次。** 这次它出现在一个大部分人不会去想"引用"的地方。

> 现在产品说："删除按钮旁边加个'举报'，管理员才能看到。"
>
> 你需要把 `currentUser.is_admin` 传到 `RowActions`。

```

```

> `currentUser` 已经传了，所以这次还算运气好。
>

```diff

-   return <TableBody questions={...} currentUser={...} />;
+   return <TableBody questions={...} currentUser={...} reportConfig={...} />;

## 三、状态归属决策树

**约 14 分钟。本次课的方法论核心。**

### 3.1 五个可能的去处

**醒目页**：

| 去处 | 谁拥有 | 生命周期 |
|---|---|---|
| **① 不存**（渲染时算） | 没有人——它是派生的 | 每次渲染 |
| **② query 层缓存** | **服务器** | 到失效为止 |
| **③ URL** | **用户**（他可以收藏、分享、后退） | 到他关闭标签页 |
| **④ Context** | 应用 | 应用运行期间 |
| **⑤ 就近 `useState`** | 那一个组件 | 组件挂载期间 |

### 3.2 决策树（**封面级素材，本次课最重要的一页**）

```
┌─ 它能从别的状态算出来吗？
│    是 → ① 不存，渲染时算
│    否 ↓
├─ 它是服务器拥有的数据吗？
│    是 → ② 交给 query 层
│    否 ↓
├─ 用户会想分享 / 刷新 / 后退到这个状态吗？
│    是 → ③ 放 URL
│    否 ↓
├─ 有多少组件需要它？
│    一个，或父子两层  → ⑤ 就近 useState
│    跨越多层 ↓
├─ 它变化频繁吗？
│    不频繁（用户、主题、语言、权限）→ ④ Context
│    频繁 → 拆分 Context，或重新设计组件结构
└─
```

**再加一个横向的问题**：

```
┌─ 它的更新规则复杂吗？（多个字段联动、有明确的状态转移）
│    是 → 用 useReducer 组织（可以配合上面任何一种归属）
│    否 → useState
```

> 注意最后这条**不是"放哪"的问题，是"怎么组织"的问题**。两者独立。

### 3.3 逐条讲，每条都回收

**① 能算出来就不要存**

> **这是第四次说这句话。**
>
> | 次课 | 场景 |
> |---|---|
> | 第 6 次课 | 不存冗余字段，能从源数据算 |
> | 第 8 次课 | 契约只有一个真相来源，其余全部生成 |
> | 第 12 次课 | 派生数据渲染时算，不用 effect + state |
> | **今天** | **状态归属决策的第一问** |
>
> **为什么说了四次还会犯？** 因为"存起来"看上去更快、更直观，而"每次算"感觉浪费。
>
> **判据：存一份副本的成本，不是那点内存，是"从此你要负责让它和源保持一致"。**
>
> 而同步这件事，**没有人能长期做对**。

```tsx
// ❌ 存了
const [filtered, setFiltered] = useState<Q[]>([]);
useEffect(() => setFiltered(items.filter(...)), [items, keyword]);

// ✅ 算
const filtered = items.filter(q => q.title.includes(keyword));
```

**② 服务端数据交给 query 层**

> **回收第 12 次课单元 8.2 那张表。**
>
> 服务端数据的特征：**会过期、别人会改、丢了重新拉一次就行**。
>
> 塞进 Context 或 Redux，你就要自己回答第 12 次课那五个问题：去重、失效、重试、共享、新鲜度。
>
> **判据：如果一个状态是通过 HTTP 拿到的，它不属于你，不要把它当成你的状态来管。**

**③ 放 URL 的判断**

**醒目页**：

| 问自己 | 答案是"是" → 放 URL |
|---|---|
| 用户会想把这个页面发给别人吗？ | 筛选、分页、排序、详情 id |
| 刷新后丢了会让用户恼火吗？ | 同上 |
| 用户会期望后退键能撤销它吗？ | 同上 |
| 搜索引擎需要索引这个状态吗？ | 分类页、标签页 |

> 反面：
>
> | 不放 URL | 理由 |
> |---|---|
> | 输入框里还没提交的字 | 每敲一个字就改一次 URL，历史记录会被塞爆 |
> | 弹窗开没开 | 分享一个"弹窗开着"的链接没有意义 |
> | 鼠标悬停在哪 | 同上 |
> | **任何敏感信息** | **URL 会进浏览器历史、服务器日志、Referer 头** |
>
> 最后一行要强调：**URL 是明文的、会被记录的。**
>
> **回收第 4 次课：日志里不能有敏感信息。** URL 会进访问日志——**所以"不要把 token 放 URL"是同一条判据。** 第 14 次课会正式讲。

**④ Context 的判断**

> 两个条件**必须同时满足**：
>
> - **跨越多层**（否则 props 就够了）
> - **变化不频繁**（否则代价太大，见单元 6.2）
>
> 典型的正当用法：
>
> | 状态 | 跨层吗 | 变化频繁吗 |
> |---|---|---|
> | 当前用户 | ✅ | ❌ 登录/登出时才变 |
> | 主题 | ✅ | ❌ |
> | 语言 | ✅ | ❌ |
> | 权限信息 | ✅ | ❌ |
>
> **注意这四个的共同点：它们都是"整个应用的背景条件"，不是"页面在做的事"。**

**⑤ 就近**

> **默认答案是这个，不是 Context。**
>
> **回收第 12 次课单元 8.4 的"状态下移"**：状态放得越高，跟着渲染的东西越多。
>
> 判据和第 4 次课的分层、第 7 次课的事务边界同构：**范围越小越好，除非有明确理由放大。**

### 3.4 一条元判据

**封面级素材**：

> **不要问"这个状态放哪方便"，问"这个状态属于谁"。**
>
> | 属于 | 就放在 |
> |---|---|
> | 服务器 | query 层 |
> | 用户（他要分享、刷新、后退） | URL |
> | 整个应用 | Context |
> | 这个组件 | 就近 |
> | 没有人（它是算出来的） | 不存 |

### 4.3 四个需要展开的

**② `currentUser`：一个状态两个归属**

> 这是全场第一个反直觉的。
>
> `currentUser` 是**服务端数据**（它来自 `/me` 接口），所以归 query 层。
> 但它又**跨越多层、变化不频繁**，所以适合 Context。
>
> **两者不冲突：**
>
> ```tsx
> // query 层负责"拿到它、缓存它、失效它"
> function useCurrentUser() {
>   return useQuery({ queryKey: ["me"], queryFn: fetchMe, staleTime: 5 * 60_000 });
> }
>
> // Context 只负责"让深层组件不用 drilling"——而且它包的是 hook，不是数据副本
> const UserContext = createContext<User | null>(null);
> function UserProvider({ children }) {
>   const { data } = useCurrentUser();
>   return <UserContext.Provider value={data ?? null}>{children}</UserContext.Provider>;
> }
> ```
>
> **判据：Context 传递的是"访问途径"，不是"数据副本"。**
>
> 区别在哪：
>
> | | 把数据拷进 Context | 用 Context 包住 query |
> |---|---|---|
> | 谁负责刷新 | **你** | query 层 |
> | 两个地方会不一致吗 | **会** | 不会，同一个缓存条目 |
> | 失效了怎么办 | 你自己处理 | `invalidateQueries` |

**④ `draftKeyword`：同一个输入框，两个状态（本单元最重要的一条）**

> 全场最反直觉的一条。**一个搜索框，需要两个状态。**

```tsx
function SearchBar() {
  const [sp, setSp] = useSearchParams();
  const keyword = sp.get("q") ?? "";                    // ③ URL 态：已提交的
  const [draft, setDraft] = useState(keyword);          // ⑤ 就近：正在输入的

  return (
    <input
      value={draft}
      onChange={e => setDraft(e.target.value)}
      onKeyDown={e => e.key === "Enter" && commit(draft)}
    />
  );
}
```

**为什么必须分开（醒目页）**：

| 如果只用 URL 态 | 如果只用本地 state |
|---|---|
| **每敲一个字就 push 一条历史记录** | **刷新丢失、不能分享** |
| 按 10 次后退才能退出这个页面 | 回到演示一 |
| 每个字符触发一次请求（除非再加防抖） | |

> **它们是两个不同的东西：**
>
> | | `draft` | `keyword` |
> |---|---|---|
> | 含义 | 用户**正在打**的字 | 用户**已经确认**要搜的词 |
> | 谁拥有 | 这个输入框 | 用户（他要分享） |
> | 变化频率 | 每个按键 | 每次回车 |
>
> **判据：如果两个值的"变化频率"或"拥有者"不同，它们就是两个状态，不要合并。**
>
> 这条判据你见过一个同构版本——**第 11 次课单元 3.3**：`pendingDeleteId` 一个状态表达了两件事，因为**那两件事不可能独立变化**。
>
> **今天是反过来的方向：两件事可以独立变化，就不要挤在一个状态里。**
>
> **两条合起来是同一条：状态的粒度，应该和"什么和什么必须一起变"对齐。**

**⑧ `expandedIds`：一个需要权衡的（诚实地给出"看情况"）**

> 直觉说：展开状态也该放 URL，这样能分享"展开了第 3 条"的页面。
>
> **但实际上：**
>
> | 放 URL | 代价 |
> |---|---|
> | `?expanded=3,17,42,88` | URL 变得很丑 |
> | 每次展开/收起都进历史 | 后退键行为奇怪 |
> | 真的有人要分享这个吗 | **通常没有** |
>
> **判据：URL 态是有成本的——它占用历史记录、暴露给所有人、长度有限。**
>
> **问"用户真的会分享这个状态吗"，而不是"这个状态理论上能不能分享"。**
>
> 我的答案是就近 `useState`。**但这是一个判断，不是规则**——如果你的产品是"分享一份展开好的阅读清单"，那答案就变了。
>
> **注意这一条和前面九条的区别：前面九条有标准答案，这一条没有。**
> **识别出"哪些问题有标准答案、哪些需要权衡"，本身就是能力的一部分。**

**⑨ `scrollPosition`：你不该写这段代码**

```tsx
// ❌ AI 常写的
useEffect(() => {
  window.scrollTo(0, scrollPosition);
}, []);
useEffect(() => {
  const h = () => setScrollPosition(window.scrollY);
  window.addEventListener("scroll", h);
  return () => window.removeEventListener("scroll", h);
}, []);
```

> **浏览器自带滚动恢复。** React Router 也有 `<ScrollRestoration />`。
>
> 你自己写的这套，**大概率不如浏览器的好**（它要处理图片加载导致的高度变化、异步内容、后退与前进的区别……）。
>
> **判据：在写一个状态之前，先问"平台是不是已经替我管了"。**
>
> 这条判据你见过两次：
> - 第 2 次课：**HTTP 缓存**——浏览器替你管了一层
> - 第 12 次课：**URL 与历史**——浏览器替你管了导航栈
>
> **今天是第三次。** 通用形式：**平台已经实现的东西，你重写一遍只会更差。**

### 4.5 把 URL 解析收敛成一道闸门（**新增护栏**）

> URL 里的东西是**用户可以随便写的**。第 12 次课单元 7.3 提过这一点，今天把它做成结构。

```ts
// src/routes/listParams.ts —— 唯一的解析入口
const SORTS = ["latest", "oldest", "views"] as const;
type Sort = typeof SORTS[number];

export interface ListParams {
  readonly q: string;
  readonly tags: readonly string[];
  readonly page: number;
  readonly sort: Sort;
}

export function parseListParams(sp: URLSearchParams): ListParams {
  const rawPage = Number(sp.get("page"));
  const rawSort = sp.get("sort");
  return {
    q: (sp.get("q") ?? "").slice(0, 100),                       // 长度闸门
    tags: (sp.get("tags") ?? "").split(",").filter(Boolean).slice(0, 10),
    page: Number.isInteger(rawPage) && rawPage > 0 ? rawPage : 1,
    sort: SORTS.includes(rawSort as Sort) ? (rawSort as Sort) : "latest",
  };
}
```

**三点要讲**：

> **一、这是第 3 次课"入口闸门"的前端版。**
>
> 当时的判据：**不可信的输入，在最外层就收窄；越往里，类型越确定。**
>
> `parseListParams` 之后，应用内部拿到的 `ListParams` 里，`page` 一定是正整数、`sort` 一定是三个字面量之一。**内部代码不需要再做任何防御。**
>
> **二、它是唯一入口。**
>
> 加一条检查（第 9 次课的固定动作）：
>
> ```js
> // eslint.config.js
> "no-restricted-syntax": ["error", {
>   selector: "CallExpression[callee.property.name='get'][callee.object.name='sp']",
>   message: "不要直接读 searchParams，用 parseListParams()",
> }],
> ```
>
> **三、它对应后端的什么。**
>
> | 层 | 闸门 | 哪次课 |
> |---|---|---|
> | 后端路径参数 | `qid: int = Path(gt=0)` | 第 9 次课 |
> | 后端排序字段 | `Literal["latest","views"]` | 第 7 次课 |
> | **前端 URL 参数** | **`parseListParams`** | **今天** |
>
> **同一道闸门，两端各一份。** 理由还是那条：**前端是体验，后端是安全**（演示四刚讲过第三遍）。

**护栏累加表新增一行（封面级素材）**：

|---|---|---|---|

**约 12 分钟。B 档，时间紧保留 5.1 和 5.4。**

### 5.1 嵌套路由解决什么

**先看问题**：

```tsx
// 每个页面都自己渲染一遍布局
function QuestionListPage() {
  return <><Header /><Sidebar /><main>...</main><Footer /></>;
}
function QuestionDetailPage() {
  return <><Header /><Sidebar /><main>...</main><Footer /></>;
}
```

> **三个问题：**
>
> | 问题 | 后果 |
> |---|---|
> | 重复 | 改布局要改每个页面 |
> | **切页面时 Header 被卸载重建** | 里面的状态丢了（比如展开的菜单） |
> | 无法做"局部加载" | 换页面时整屏白一下 |

**嵌套路由**：

```tsx
<Routes>
  <Route path="/" element={<AppLayout />}>          {/* 外层：Header + Sidebar + <Outlet/> */}
    <Route index element={<QuestionListPage />} />
    <Route path="questions/:qid" element={<QuestionDetailPage />}>
      <Route path="answers" element={<AnswerList />} />     {/* 再嵌一层 */}
    </Route>
    <Route path="settings" element={<SettingsLayout />}>
      <Route path="profile" element={<Profile />} />
      <Route path="notifications" element={<Notifications />} />
    </Route>
  </Route>
  <Route path="*" element={<NotFound />} />
</Routes>
```

```tsx
function AppLayout() {
  return (
    <>
      <Header />
      <Sidebar />
      <main><Outlet /></main>      {/* ← 子路由渲染到这里 */}
      <Footer />
    </>
  );
}
```

> **切换页面时，`AppLayout` 不会被卸载。** Header 里的状态活着，只有 `<Outlet/>` 的内容换了。
>
> **回收第 11 次课单元 4.3 的 diff 规则一：类型不同，整棵子树销毁重建。**
>
> 嵌套路由做的事，正是**让稳定的那部分保持同一个位置、同一个类型**，从而复用实例。

### 5.2 路由参数变化时，要不要重建

**回收第 11 次课 4.3 结尾那个技巧**：

```tsx
// 从 /questions/1 切到 /questions/2
function QuestionDetailPage() {
  const { qid } = useParams();
  const [draftComment, setDraftComment] = useState("");   // ← 用户写了一半的评论
  ...
}
```

> **组件类型没变、位置没变 → React 复用实例 → `draftComment` 不会清空。**
>
> 用户给问题 1 写了一半评论，点到问题 2，**那半条评论还在输入框里**。
>
> **这是 bug 还是特性？看需求。** 想要清空：
>
> ```tsx
> <QuestionDetailPage key={qid} />      // ← key 变了 → 强制重建 → state 清零
> ```
>
> **这是 key 的第五次出现，而且是唯一一次"主动利用重建"。**
>
> | 场景 | key 的作用 | 哪次课 |
> |---|---|---|
> | 数据库主键 | 标识一行 | 第 6 次课 |
> | 列表 key | 标识一个组件实例 | 第 11 次课 |
> | 强制重建 | **故意让标识改变** | 第 11 次课提及 |
> | queryKey | 标识一份缓存 | 第 12 次课 |
> | **路由 key** | **让切换问题时清空草稿** | **今天** |

### 5.3 路由守卫：它能做什么，不能做什么

```tsx
function RequireAuth({ children }: { children: ReactNode }) {
  const user = useContext(UserContext);
  const location = useLocation();
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;
  return <>{children}</>;
}

<Route path="settings" element={<RequireAuth><SettingsLayout /></RequireAuth>} />
```

**必须立刻接一句（回收演示四）**：

> **这跟演示四那个 `&&` 是同一个东西。**
>
> 路由守卫**只是让用户少看到一个没用的页面**。它不保护任何数据——数据在后端，后端不认这个守卫。
>
> **判据：路由守卫是导航体验，不是访问控制。**
>
> 一个自检：**把你的路由守卫全部删掉，后端有没有变得更不安全？**
>
> **答案应该是"没有"。如果是"有"，说明你的后端有问题。**
>
> → 第 15 次课会正面做这件事。

### 5.4 `lazy`：接上第 10 次课的代码分割

> **第 10 次课我们做过一次动态 `import()`，当时说"按路由拆分是它最标准的用法"。今天兑现。**
>

**但要给三条代价**：

| 代价 | 说明 |
|---|---|
| 切页面时会有一次网络请求 | 慢网下会看到 fallback 闪一下 |
| **拆太碎反而更慢** | HTTP/2 下影响小，但请求数仍有开销 |
| **fallback 必须撑住布局** | 否则会跳动（CLS） |

> **判据：按路由拆是安全的默认；再往下拆，要有量化依据（第 10 次课的 visualizer）。**

## 六、Context 与 `useReducer`

**约 14 分钟。**

### 6.1 Context 解决的是 prop drilling，不是"状态管理"

**封面级素材**：

> **Context 是一个"传递"机制，不是一个"存储"机制。**
>
> 它做的事只有一件：**让深层组件不用逐层接力。**
>
> 它**不提供**：缓存、失效、订阅粒度、持久化、时间旅行、中间件。
>
> **把它当 Redux 用，你会得到一个没有任何优化的 Redux。**

### 6.2 量一下 Context 的代价（**用第 11 次课的工具**）

**现场演示，三步**：

**第一步：一个大 Context**

```tsx
<AppContext.Provider value={{ theme, user, keyword, page, isFilterOpen, ... }}>
```

```
切换主题 → renderCounts.QuestionRow = 1000
```

**第二步：拆成两个**

```tsx
<ThemeContext.Provider value={theme}>
  <UserContext.Provider value={user}>
```

```
切换主题 → renderCounts.QuestionRow = 0      ← 表格不读 theme
```

**第三步：暴露 `value` 是新对象的问题**

```tsx
// ❌
<UserContext.Provider value={{ user, logout }}>

// ✅
const ctx = useMemo(() => ({ user, logout }), [user, logout]);
<UserContext.Provider value={ctx}>
```

```
父组件任意渲染 → 改之前：所有消费者渲染
                 改之后：0
```

**醒目页**：

| Context 的三条纪律 | 理由 |
|---|---|
| **按"变化频率"拆分**，不按"业务模块"拆 | 一起变的放一起 |
| **`value` 必须引用稳定**（`useMemo`） | 引用判等，第四次 |
| **把"状态"和"更新函数"拆成两个 Context** | 只调用不读取的组件，就不会被通知 |

第三条要展开：

```tsx
const StateContext = createContext<S | null>(null);
const DispatchContext = createContext<Dispatch<A> | null>(null);
```

> `dispatch` 的引用**永远稳定**（React 保证）。
>
> 于是：**只 dispatch 不读 state 的组件（比如一个"清空筛选"按钮），永远不会因为 state 变化而重渲染。**

### 6.3 什么时候 Context 不够

**醒目页**：

| 症状 | 说明 |
|---|---|
| 一个 Context 里的字段变化频率差异很大，**拆了七八个还在拆** | 组件结构可能有问题 |
| 需要**只订阅某个字段** | Context 做不到，要么拆，要么上库 |
| 需要在 React 之外读写状态 | 用 `useSyncExternalStore` 或库 |
| 需要持久化 / 时间旅行 / 中间件 | 上库 |

> **判据（回收第 12 次课单元 8.5）：当你第三次实现同一个机制时，考虑上库。**
>
> 但今天要加一条更具体的：
>
> **在考虑状态管理库之前，先确认你的状态归属是对的。**
>
> **很多"需要状态管理库"的感觉，其实是"服务端数据放错了地方"。** 把服务端状态交给 query 层之后，剩下的客户端状态通常少到用 Context 就够了——**单元 4 的改造就是证据：9 个字段变成了 2 个。**

### 6.4 `useReducer`：什么时候值得

**先给一个 `useState` 已经撑不住的例子**：

```tsx
// 一个提交表单的状态：四个 useState，它们之间有隐含的约束
const [submitting, setSubmitting] = useState(false);
const [error, setError] = useState<string | null>(null);
const [result, setResult] = useState<Q | null>(null);
const [touched, setTouched] = useState(false);
```

> **问题：这四个状态可以组合出 2×2×2×2 = 16 种情况，而合法的只有 4 种。**
>
> 非法组合比如：`submitting=true` 且 `error !== null`（正在提交，同时又有错误？）
>
> **而且没有任何东西阻止你写出非法组合。**

**改成 reducer**：

```tsx
type State =
  | { kind: "idle" }
  | { kind: "submitting"; payload: QuestionCreate }
  | { kind: "error"; message: string; payload: QuestionCreate }
  | { kind: "success"; data: QuestionOut };

type Action =
  | { type: "SUBMIT"; payload: QuestionCreate }
  | { type: "SUCCEEDED"; data: QuestionOut }
  | { type: "FAILED"; message: string }
  | { type: "RESET" };

function reducer(s: State, a: Action): State {
  switch (a.type) {
    case "SUBMIT":
      if (s.kind === "submitting") return s;          // ← 转移规则写在这里
      return { kind: "submitting", payload: a.payload };
    case "SUCCEEDED":
      return s.kind === "submitting" ? { kind: "success", data: a.data } : s;
    case "FAILED":
      return s.kind === "submitting"
        ? { kind: "error", message: a.message, payload: s.payload } : s;
    case "RESET":
      return { kind: "idle" };
  }
}
```

**三点价值（醒目页）**：

| 价值 | 说明 | 回收自 |
|---|---|---|
| **非法状态不可表示** | 16 种组合塌缩成 4 种 | 第 8 次课可辨识联合 |
| **非法转移被显式拒绝** | `SUBMIT` 在 submitting 时被忽略 → **防重复提交** | 第 3 次课幂等 |
| **转移规则集中在一处** | 不散落在各个事件处理函数里 | — |

> 第二条值得停一下：**`if (s.kind === "submitting") return s;` 这一行，就是一个结构性的防重复提交。**
>
> 它比 `disabled` 强——**因为 `disabled` 在 DOM 上，这个在状态机里**。
>
> **但它仍然只在前端。** 演示四那条判据第四次出现：**后端的唯一约束才是保证。**

**什么时候不值得**：

| 情况 | 用什么 |
|---|---|
| 一两个独立的布尔值 | `useState` |
| 状态之间没有约束 | `useState` |
| **多个字段必须一起变** | `useReducer` |
| **有明确的"阶段"** | `useReducer` |
| **需要禁止某些转移** | `useReducer` |

> 判据：**当你发现自己在连续调用三个 `setXxx`，并且它们必须同时成功时，就该用 reducer 了。**

- **封面级素材**：6.1 的"Context 是传递机制，不是存储机制"。
- **封面级素材**：6.2 的三条纪律 + 三步演示的 `renderSpy` 数据。
- **封面级素材**：6.3 的"先确认状态归属，再考虑状态管理库"（**配 9 → 2 的字段数对比**）。

## 七、渲染模式：回到第 5 次课那个页面

**约 12 分钟。本次课第三个高光。**

### 7.1 你已经写过一个 SSR 版本了

**打开第 5 次课学生自己写的 Jinja2 页面。**

```python
@app.get("/questions", response_class=HTMLResponse)
def question_list(request: Request, db: Session = Depends(get_db)):
    questions = repo.list_questions(db, page=1)
    return templates.TemplateResponse("list.html", {"request": request, "questions": questions})
```

> **这就是服务端渲染。**
>
> 第 5 次课我们没这么叫它，因为当时没有对照物。**现在有了。**
>
> **同一个功能、两套实现、都是你们自己写的。** 今天把它们放在一起量一次。

### 7.2 实测对照（**现场做，不要只给结论**）

**测法**：清空缓存 → 打开 Network → 勾选 "Disable cache" → 用 Slow 3G 节流 → 访问首页。

| 指标 | **SSR（第 5 次课的 Jinja2）** | **CSR（现在的 SPA）** |
|---|---|---|
| 首屏 HTML 里有内容吗 | **有，完整的列表** | **没有，只有 `<div id="root">`** |
| 首屏请求数 | **1**（HTML 里就有数据） | **3**（HTML → JS → API） |
| 首屏出现文字的时间（Slow 3G） | **~0.9s** | **~4.2s** |
| 白屏期间用户看到 | 什么都没有，然后一次性出现 | **白屏 → 骨架屏 → 内容** |
| 禁用 JS 还能看吗 | **能** | **不能** |
| 搜索引擎能抓到内容吗 | **能** | 看情况（现代爬虫能执行 JS，但慢且不保证） |
| 点"下一页" | **整页刷新，回到顶部** | **局部更新，位置保持** |
| 点"下一页"的传输量 | **整个 HTML（~40 kB）** | **JSON（~4 kB）** |
| 交互响应 | 每次都要往返服务器 | 本地即时 |
| 部署复杂度 | **一个进程** | 静态文件 + API，或反代 |

**封面级素材，核心句**：

> **SSR 首屏快，CSR 交互快。**
>
> **这不是"谁更好"，是"你的用户在做什么"。**

### 7.3 四种模式的判据

**醒目页**：

| 模式 | 内容在哪生成 | 适合 |
|---|---|---|
| **SSG**（静态生成） | **构建时** | 内容很少变、所有人看到的一样：文档、博客、落地页 |
| **SSR**（服务端渲染） | **每次请求时** | **内容因人而异 + 首屏重要**：电商详情、社区列表 |
| **CSR**（客户端渲染） | **浏览器里** | **交互密集、登录后才用**：后台管理、编辑器、仪表盘 |
| **ISR / 增量** | 构建时 + 定期重生成 | 量大但更新不频繁：商品目录 |

**两个问题定位（封面级素材）**：

```
┌─ 内容对所有人都一样吗？
│    是 → 能不能构建时就生成？→ SSG
│    否 ↓
└─ 首屏速度重要吗？（用户是不是第一次来、是不是从搜索引擎来）
     是 → SSR
     否 → CSR
```

> **判据：登录后才能用的界面，首屏速度通常不重要**——用户已经在你的应用里了，他不会因为慢 1 秒就走。
>
> **而落地页、商品页、文章页，慢 1 秒就是真的会走。**

### 7.4 混合与水合的代价

> 现代框架（Next.js / Remix / Nuxt）做的是**混合**：首屏 SSR，之后接管成 CSR。
>
> 听起来是两全其美。**但它有代价：**

**醒目页**：

| 代价 | 说明 |
|---|---|
| **水合（hydration）** | 浏览器拿到 HTML 后，**还要下载同样那套 JS，再"认领"一遍 DOM**。这期间页面**看得见但点不动** |
| **代码要能两边跑** | 不能随便用 `window`、`document`；依赖库也得支持 |
| **需要一个 Node 服务** | 不再是纯静态部署 |
| **数据获取要分两处考虑** | 服务端首次取、客户端后续取，两套路径 |

> **"看得见但点不动"这个阶段，是 SSR 特有的问题。**
>
> 它在指标上叫 **TTI（可交互时间）远大于 FCP（首次内容绘制）**。用户看到按钮，点了没反应——**体验上有时比 CSR 的骨架屏更糟**，因为骨架屏明确告诉你"还没好"。
>
> **判据：SSR 不是免费的首屏加速，它是把"白屏"换成了"假可用"。** 要不要换，看你的场景。

**给一条务实的建议**：

> **不要为了 SSR 而引入 Next.js。**
>
> 先问：
>
> | 问题 | 如果答案是"否" |
> |---|---|
> | 需要 SEO 吗 | **不需要 SSR** |
> | 用户是不是大多首次访问 | 不是 → 不需要 |
> | 首屏慢会损失用户吗 | 不会 → 不需要 |
>
> **回收第 10 次课、第 12 次课：引入一个东西之前，先说清"如果不用它，我要自己写哪些东西"。**
>
> 我们这个项目（登录后使用的问答后台），**CSR 是正确答案**。

### 7.5 那第 5 次课白写了吗

> **没有。三个理由：**
>
> | 理由 | 说明 |
> |---|---|
> | 它是这一课的对照物 | **没有它，今天这节课只有结论没有证据** |
> | 模板渲染仍然大量使用 | 邮件、PDF、报表、后台管理、错误页 |
> | **自动转义那道护栏仍然有效** | 第 5 次课那条 XSS 防线，第 15 次课会回来 |
>
> **更重要的一点：** 第 5 次课那个版本让你知道了"不用 React 也能做出来"。
>
> **判据：知道一个技术的替代方案长什么样，你才有资格说"我选了它"。** 否则你只是在用你唯一会的东西。

### 8.1 M4 是什么

> **M4 = 一个完整的、可部署的单页应用，前后端契约对齐、状态归属清晰、有性能守卫。**

**验收清单（醒目页）**：

| # | 项 | 怎么验 |
|---|---|---|
| 1 | 至少 4 个路由，含一层嵌套布局 | 路由表截图 |
| 2 | **所有筛选/分页/排序在 URL 里**，刷新与分享正确 | 录屏 |
| 3 | **URL 参数经过唯一的解析闸门**，非法值不崩 | 手输 `?page=-5&sort=x` 截图 |

| 6 | 至少一处 `useReducer`，用可辨识联合 | 代码 |
| 7 | 路由级 `lazy` 拆分，主包体积下降 | 构建产物前后对比 |
| 8 | **渲染次数守卫**：切换主题/打字时列表渲染数为 0 | 测试红绿截图 |
| 9 | 所有 props 类型来自 `api.d.ts`，零 `any`、零 `as`（例外须注释） | CI |
| 10 | `tsc` + `eslint --max-warnings 0` + 契约一致性检查全绿 | CI 截图 |
| 11 | **竞态已消除**（第 12 次课的守卫仍通过） | 测试 |
| 12 | `docs/decisions.md` 记录所有关键取舍 | 文档 |

### 8.2 状态归属表（**M4 的核心交付物**）

**格式（封面级素材）**：

| 状态 | 类型 | 归属 | 理由 | 如果放错会怎样 |
|---|---|---|---|---|
| `questions` | 服务端 | query 层 | 服务器拥有、会过期 | 手写同步、两处不一致 |
| `keyword` | URL 态 | `?q=` | 要分享、刷新、后退 | 刷新丢失 |
| `draftKeyword` | UI 态 | SearchBar 内部 | 每按键变化；用户未确认 | 每个字符一条历史记录 |
| `currentUser` | 服务端 + 跨层 | query + Context | 跨层、不频繁；但仍是服务端数据 | 登出后不刷新 |
| `theme` | 应用态 | ThemeContext | 跨层、不频繁 | 与列表挤一起 → 1000 次渲染 |
| `isFilterOpen` | UI 态 | FilterPanel 内部 | 分享无意义 | 提升到全局 → 无谓渲染 |
| `scrollPosition` | **不存** | 浏览器 | 平台已实现 | 自己写的更差 |

> **最后一列是评分重点。**
>
> 不是"我把它放对了"，是"**我知道放错了会付出什么代价**"。
>
> **判据：能说出代价，才说明你做的是决策，不是猜测。**

### 8.3 一句提醒

> M4 交付的不是"页面做完了"，是"**每一个状态你都能说出它属于谁**"。
>
> 一年后你回来改这个项目，**决定你改得快不快的，不是组件写得多漂亮，是状态放得对不对。**

## 九、C 档结论卡

**约 3 分钟。时间不够整体跳过。**

| 问题 | 结论 |
|---|---|
| Zustand / Jotai / Redux Toolkit 选哪个 | **先把服务端状态交给 query 层，再看还剩多少。** 通常剩下的不需要库 |
| Context 性能真的那么差吗 | 差的不是 Context，是"**把不相关的东西放一起**"。拆对了它很快 |
| `useSyncExternalStore` | 订阅外部数据源的官方 API，是所有状态库的底层。自读 |
| 表单库（React Hook Form 等） | 大表单值得。它主要解决**非受控 + 校验 + 性能**三件事 |
| URL 里能放多少 | 实际上限约 2000 字符（浏览器/服务器各有限制）。**长状态考虑存服务端返回一个 id** |
| 路由数据加载（loader） | React Router 的 `loader` / Remix 的模式：**在渲染之前就开始取数据**，能消掉瀑布流 |
| 微前端 | 解决的是**组织问题**（多团队独立发布），不是技术问题。小团队不需要 |
| 动画与路由切换 | `AnimatePresence` 之类需要 key 稳定。**又是 key** |
| 状态持久化到 localStorage | 可以，但要处理**版本迁移**和**跨标签页同步**。别随手用 |
| SSR 下的 CSS | 要处理 FOUC。这是引入 SSR 的隐性成本之一 |
