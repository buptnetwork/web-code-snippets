## 二、解剖台：一段能跑的 AI 代码，你从哪里开始查

**约 14 分钟。这是本次课的动机来源，不要做成找错游戏。**

### 情境设定（先给情境，再给代码）

给学生一个具体处境，不要抽象描述：

> 你把这个项目交给同学试用。半小时后他说："搜索有时候出不来东西。" 你问他搜的什么，他说忘了。你打开自己的电脑试了三次，都正常。
>
> 现在，你从哪里开始查？

让学生看代码，回答三个问题（**这是本次课版本的解剖三问，与后续课的三问不同**）：

1. 这段代码在请求链路的哪个位置起作用？
2. 如果它出问题，你会在哪里看到迹象？
3. 现在这个版本，你有办法查吗？

### 代码（tag: `v1-ai-raw`，AI 生成，可运行，教学反例）

```python
# app/ai_version.py —— AI 生成版本，可运行，用于解剖，不是最终实现
import os
from fastapi import FastAPI
from sqlalchemy import create_engine, text

app = FastAPI()

DATABASE_URL = "postgresql+psycopg://webuser:webpass@localhost:5432/webcourse"
API_TOKEN = "sk-demo-8f3a91c0b7"

engine = create_engine(DATABASE_URL)

@app.post("/getQuestions")
def get_questions(keyword: str = "", page: int = 1):
    with engine.connect() as conn:
        rows = conn.execute(text(
            f"SELECT * FROM questions "
            f"WHERE title LIKE '%{keyword}%' "
            f"LIMIT 20 OFFSET {(page - 1) * 20}"
        )).fetchall()
    return {"success": True, "data": [dict(r._mapping) for r in rows]}

@app.post("/getQuestionDetail")
def get_question_detail(qid: int):
    with engine.connect() as conn:
        row = conn.execute(text(f"SELECT * FROM questions WHERE id = {qid}")).fetchone()
    if row is None:
        return {"success": False, "message": "not found"}
    return {"success": True, "data": dict(row._mapping)}
```

### 期望的收敛过程

学生大概率会找出"密钥写死了""SQL 拼字符串"这类他们听说过的问题。**接住，但不要展开**，把它们记在黑板一侧的"欠账清单"上，标明在第几次课还：

| 发现的问题 | 本次课处理方式 | 何时还 |
|---|---|---|
| 密钥硬编码 | 今天只做最低限度的 `os.getenv` | 第 4 次课（配置外置） |
| SQL 字符串拼接 | 今天只标记"这里将来会出事" | 第 6 次课、第 15 次课（注入） |
| `SELECT *` 直接返回全部列 | 今天只指出"你不知道返回了什么" | 第 3 次课（response_model） |
| URI 用动词 `/getQuestions` | 今天点名 | 第 8 次课（资源化 URI） |
| 读操作用 POST | **今天回收**（单元 9） | — |
| 错误返回 `200 + success:false` | **今天回收**（单元 9） | — |

然后把学生带到真正的落点上。用提问推进，不要直接宣布：

> 好，这些都对。现在回到同学那句话——"搜索有时候出不来东西"。上面这些问题，哪一个能帮你查清楚他到底遇到了什么？

答案是：一个都不能。

### 本单元的结论（这是全课的动机，请做成醒目的一页）

> **这段代码最大的问题不是某一行写错了。是它整个是不可观察的。**
>
> 它没有日志，所以你不知道请求有没有到；
> 它无论成败都返回 200，所以你不知道它是否失败；
> 它没有任何标识，所以就算有日志，你也不知道哪一条属于同学那次请求。
>
> 一段不可观察的代码，出问题时你只能靠猜。AI 生成的代码默认就是这样的——因为你没要求它可观察。

讲：

> 我特意没有把这段代码写得很烂。它能跑，缩进整齐，甚至用了连接上下文管理器。它就是你们平时会拿到的那种代码。今天要建立的第一个判断标准是：**代码"能跑"和"能查"是两件事，后者需要你专门要求。**

## 三、请求全链路：八个环节与三问表

**约 13 分钟。本单元是纯讲授 + 一张核心图，注意控制在 10 分钟出头，不要超过 15。**

### 内容

从浏览器地址栏敲回车，到页面出现内容，请求经过下面这些环节。本次课的开发环境里有些环节被省略（比如没有反向代理），但先把完整的位置留出来，后面的课会逐个填。

**核心图：请求全链路图 v1**

图的要素与关系（画法交给制作团队）：

- 横向从左到右八个环节：`浏览器` → `名称解析与连接（DNS/TCP/TLS）` → `反向代理（生产环境才有，本课灰显）` → `ASGI 服务器 uvicorn` → `中间件链` → `路由与参数解析` → `应用代码` → `数据库`；末端有一条回程箭头返回浏览器并触发渲染。
- **四处观察点用统一的标记挂在对应环节上**：观察点①在"浏览器"（DevTools 报文）；观察点②在"中间件链"（应用日志）；观察点③在"应用代码"（断点栈帧）；观察点④在"数据库"前的调用处（SQL 日志）。这四个标记的样式要在全课件中保持一致，后面每个单元都会回到这张图上高亮其中一个。
- 灰显的"反向代理"上标注"第 16 次课填"。

**核心表：三问表**（这张表学生作业要自己重填，请做成可读性优先的大表，必要时分两页）

| 环节 | 谁负责 | 典型失败表现 | 在哪观察 |
|---|---|---|---|
| 浏览器构造请求 | 你的前端代码 / 表单 | 请求根本没发出；方法或 URL 发错 | DevTools Network：**先确认这条请求是否存在** |
| 名称解析与连接 | 操作系统 / 网络 / DNS / 证书 | `ERR_NAME_NOT_RESOLVED`、连接超时、证书错误 | Network 里显示 failed 且**没有状态码**；`curl -v` |
| 反向代理（生产） | Nginx 等 | 502 / 504；静态文件 404 | 代理访问日志（第 16 次课） |
| ASGI 服务器 | uvicorn | 端口没监听、进程崩溃、启动即报错 | **启动终端的输出** |
| 中间件链 | 你写的中间件 | 所有请求都被拦住；响应头缺失 | 应用日志 |
| 路由与参数解析 | 框架 | 404（路径不匹配）、422（参数不合法） | 响应体 + `/docs` |
| 应用代码 | 你 | 500 + 异常栈；**逻辑错了但返回 200** | 应用日志 + 断点栈帧 |
| 数据库 | PostgreSQL | 连不上、SQL 报错、查得很慢 | SQL 日志 |

### 需要强调的两条判据

**判据一：有没有状态码，是一条分界线。**
如果 Network 里这条请求连状态码都没有，说明请求根本没到达应用——问题在链路前半段（连接、地址、跨域、服务没起）。如果有状态码，哪怕是 500，也说明服务端收到了并回答了。这一条能把排查范围直接砍掉一半。

**判据二：先确认请求是否存在，再讨论它对不对。**
学生最常见的错误是一上来就改后端代码，而实际上请求压根没发出去。

讲：

> 这张表里"在哪观察"那一列是今天的重点。你们现在的状态是：知道"哪里可能坏"，但不知道"坏了以后去哪里看"。今天把其中四个位置的观察方法一次装齐。

（补充给制作团队：这张表的适用范围要标明——它描述的是**本课程使用的技术栈与开发环境**下的常见情况，不是所有 Web 系统的通用故障手册。生产环境会多出 CDN、负载均衡、容器编排等环节。）

## 四、观察点①：报文——服务端与客户端之间唯一真实的东西

**约 14 分钟。这是第一个动手单元。**

### 内容

先启动项目（tag `v1-ai-raw`），三个动作：

1. **用 `/docs` 发一次请求。** 说明这个页面是框架根据你的函数签名自动生成的，第 3 次课会讲它从哪来；今天只把它当一个"能发请求的工具"。
2. **用浏览器 DevTools Network 看这次请求的四个部分**：请求行（方法 / 路径 / 协议版本）、请求头、请求体、以及响应的状态行 / 响应头 / 响应体。**请求与响应各是四部分（含空行）**，这个结构在第 2 次课会展开成协议语义，今天只要求认得出来。
3. **用 curl 复现同一次请求**：

```bash
curl -i -X POST "http://localhost:8000/getQuestions?keyword=react"
```

`-i` 让响应头一起打印出来。这一步的意义不是学 curl，而是让学生意识到：**浏览器并不特殊，它只是一个会发 HTTP 报文的程序**。任何能发报文的东西都能替代它。这一点在后面"绕过前端直接测后端"时反复用到。

### 顺带讲清 URL 各段（若时间紧，压成一张图带过）

用一个带全部成分的地址标注：`https://` 协议 / `api.example.com` 主机 / `:8000` 端口 / `/questions` 路径 / `?keyword=react&page=2` 查询串 / `#top` 片段。

**留一个判据**：`#` 之后的片段**不会发送到服务器**，它只在浏览器内部使用。这一条在第 13 次课讲路由时回收。

### 讲

> 报文是客户端和服务端之间唯一真实存在的东西。你前端写了什么、后端框架怎么封装，对方都看不见，它们只看到这段报文。所以当前后端互相甩锅时，第一件事永远是：把报文调出来，我们一起看。

### 材料

- 演示项目 tag `v1-ai-raw`，启动方式见 README（`uv run uvicorn app.ai_version:app --reload`）。
- 数据来自 `seed.sql`，三张表（questions / answers / tags）约 50 行样例数据，均为虚构内容。
- 截图需求：DevTools Network 中某条请求的 Headers 面板，**需要放大的区域是请求行与状态行**，其余保留环境概览即可。请不要用整屏截图让学生找小字。

## 五、观察点②：应用日志——以及它为什么默认是没用的

**约 14 分钟。本单元包含"痛感 → 命名"的关键设计，请严格按顺序展开，不要提前给出 request-id。**

### 第一步：先加日志，看起来问题解决了

在应用里加最朴素的日志：

```python
import logging
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)
logger = logging.getLogger("app")
```

在端点里打一条 `logger.info("query keyword=%s page=%s", keyword, page)`，发一次请求，终端出现一行。学生此时会觉得："这不就行了吗。"

### 第二步：制造噪音，打破直觉（**这是本单元的关键，必须现场做**）

打开第二个终端，跑课程提供的 `bench.sh`（或 `bench.py`），并发发出 10 个请求，其中混入你自己在浏览器点的 1 个。

现在终端里是十几行交织的日志。向学生提出问题：

> 刚才我点的那一次，是这里面的哪一行？下一行的日志还是不是同一个请求的？

学生做不到。**这就是本次课要解决的问题。**

补充一个更难的情形：如果一个请求内部打了五条日志（进入、查库前、查库后、组装、返回），并发之下这五条会被其他请求的日志切碎，你无法把它们重新组装成一次完整的经过。

### 第三步：命名并实现——request-id

现在给出概念：**为每个请求生成一个唯一标识，让这次请求产生的所有记录都带上它。** 这个标识叫 request-id（也叫 correlation id、trace id）。

现场加入中间件（演进到 tag `v2-traceable`）：

```python
import time, uuid
from fastapi import Request

@app.middleware("http")
async def trace_middleware(request: Request, call_next):
    rid = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
    request.state.request_id = rid
    start = time.perf_counter()
    logger.info("[%s] --> %s %s", rid, request.method, request.url.path)

    response = await call_next(request)

    cost = (time.perf_counter() - start) * 1000
    logger.info("[%s] <-- %s %.1fms", rid, response.status_code, cost)
    response.headers["X-Request-ID"] = rid
    return response
```

三个设计要点要讲出来，不要只贴代码：

- **优先采用调用方传来的 id**（`request.headers.get(...)`），没有才自己生成。这样上游系统或前端已经有的 id 能贯穿下来。
- **把 id 放进 `request.state`**，让端点函数里也能拿到它打日志。
- **把 id 写回响应头**。这一条的现实意义：用户报障时，他能截图给你这个 id，你直接 grep 就能定位到那一次。这是工业界的常规做法。

重跑并发实验，然后：

```bash
grep "a3f91c22e0d7" server.log
```

一次请求的完整经过被干净地筛出来。**两次实验的日志截图请同屏对照，这是本单元的高光。**

### 第四步：诚实交代这个版本的局限（**请务必保留，不要删**）

现场演示一个必崩的端点（`/boom`），观察日志：只有 `-->`，没有 `<--`。

原因：异常发生时 `call_next` 抛出，中间件后半段没有执行。

结论与欠账：

> 所以当前这个中间件，**在最需要它的情况下（出错时）反而失灵**。这不是实现得不好，是这个写法本身的边界。第 4 次课加全局异常处理器时会修好它。今天你要带走的是：**任何观测手段都有它失灵的场景，你得知道它的边界在哪。**

讲：

> 这一段我想让你们记住的不是 `uuid.uuid4()` 这个函数。是这个动作本身：当你发现"看不清"的时候，正确的反应不是更努力地盯着看，而是**给要观察的东西打上标记**。这个思路后面还会出现——第 9 次课查 bug、第 16 次课排查线上故障，用的都是同一招。

## 六、观察点③：断点栈帧——链路图不是我画的，是调试器里真实存在的

**约 10 分钟。这是本次课的高光之一，请优先制作。**

### 内容

在端点函数的查询语句那一行下断点，用 VS Code 的调试配置启动（课程提供 `.vscode/launch.json`），再发一次请求。程序停住。

**重点不在变量面板，在 Call Stack（调用栈）面板。**

从栈顶往下读，学生会看到类似这样一串（具体名称随版本变化，讲的时候按实际显示读）：

```
get_questions            ← 你写的函数
...                      ← FastAPI 的路由与参数解析
...                      ← 你刚写的 trace_middleware
...                      ← Starlette 应用对象
...                      ← uvicorn 的协议处理
```

**把它和单元三的链路图并排放，逐层连线。**

### 结论

> 我在第三个单元画的那张链路图，不是一个比喻，也不是教学上的简化。它就在你的调试器里，是真实存在的函数调用栈。你的代码确实是被中间件包着的，中间件确实是被服务器包着的。
>
> 这也解释了为什么中间件叫"中间"——**它在调用栈上真的处于服务器和你的业务代码之间**。第 5 次课讲"洋葱模型"时，你会再看到这张栈。

### 讲

> 顺带说一件事：很多人学了半年编程，从来没用过调试器，遇到问题就到处插 print。print 告诉你"某个时刻某个值是多少"，调用栈告诉你"你是怎么走到这里来的"。后者在读别人写的代码——包括 AI 写的——时价值大得多。

（这里有一个语言/工具知识的插入：VS Code 调试器的基本操作。请只讲四个按钮——继续、单步跳过、单步进入、停止，以及 Call Stack 和 Variables 两个面板，**讲完立刻回到追踪主线**，不要展开条件断点、监视表达式等内容。）

### 材料与备用方案

- 需要 `.vscode/launch.json`，配置为以调试模式启动 uvicorn 且**关闭 `--reload`**（reload 模式下断点行为不稳定，这一点请在课件的操作提示里写出来，是个高频踩坑点）。
- **备用**：现场调试若 30 秒内没停到断点，切换到预录的 40 秒屏幕录像（需提前录制，录像中要能看清 Call Stack 面板的完整内容）。

## 七、观察点④：SQL 日志——应用到底对数据库说了什么

**约 8 分钟。可以与上一单元连续演示：断点就停在查询前，正好接着看查询发出去的样子。**

### 内容

打开引擎的 SQL 回显：

```python
engine = create_engine(DATABASE_URL, echo=True)
```

再发一次请求，终端里出现实际执行的 SQL 语句与参数。

三个要看的点：

1. **你写的 SQL 和实际执行的 SQL 是否一致**。今天是手写 SQL，基本一致；到第 7 次课用 ORM 时，这两者会差很远，那时候 SQL 日志是唯一能看清真相的地方（N+1 问题就是这么被发现的）。
2. **一次请求发了几条 SQL**。今天是 1 条。请学生记住这个数字，第 7 次课会看到同样一个页面发出 101 条。
3. **参数是怎么传的**。本版本是字符串拼接，参数直接长在语句里。请在这里埋一句："记住这个画面，第 15 次课我们会用它把数据库拖走。"

### 一个要诚实说明的问题

`echo=True` 打出来的 SQL **不带 request-id**，它和应用日志默认是对不上的。

今天的处理方式是一个够用但不完美的办法：在查询前后各打一条带 rid 的日志，把 echo 的输出夹在中间。

```python
logger.info("[%s] sql:begin search", rid)
rows = conn.execute(...).fetchall()
logger.info("[%s] sql:done rows=%d", rid, len(rows))
```

明确告诉学生这是权宜之计：并发高的时候，夹在中间的 echo 输出仍可能和别的请求交织。真正的做法是把 rid 注入到数据库日志或用链路追踪工具，第 16 次课给结论。

> **这个坦白很重要，请在课件里保留。** 它示范了本课程要求的表达方式：给出方案的同时说明它的适用条件，而不是把权宜之计说成标准答案。

## 九、回到解剖台：为什么"200 + success:false"和"读操作用 POST"是真问题

**约 7 分钟。前面所有铺垫都是为了让这一段有说服力。**

### 先回收：错误也返回 200

现在学生已经装好了四处观察点，这时问：

> 我们已经能追踪请求了。但如果每个请求无论成败都返回 200，你追踪到的信息里，有"这次失败了"吗？

没有。日志里 `<-- 200`，Network 里绿色，一切正常。

**状态码不是给人看的注释，是给机器看的信号。** 依赖它的机器有一整排：

| 谁在读状态码 | 返回 200 + success:false 的后果 |
|---|---|
| 浏览器 DevTools | 请求全绿，你无法从列表里一眼挑出失败的那些 |
| 监控与告警系统 | 统计出的错误率是 0%，**真实故障不会触发告警** |
| 缓存与 CDN | 会把这个"成功"响应缓存起来，错误被缓存并分发 |
| 反向代理、负载均衡 | 认为后端健康，不会摘除故障实例 |
| 客户端重试逻辑 | 不知道该不该重试 |
| 你的前端代码 | 每一个调用点都得自己解包判断，**漏掉一处就是静默失败** |

状态码三大类的判据（今天只到大类，细分在第 2 次课）：

- **2xx**：服务端认为这次请求成功了。
- **4xx**：你（客户端）的请求有问题，**原样重试没有意义**。
- **5xx**：服务端出问题了，**重试可能有用**。

这条"4xx 别重试、5xx 可以重试"的判据，第 8 次课讲幂等和重试时会直接用到。

### 再回收：读操作不该用 POST

`/getQuestions` 是纯读取，却用了 POST。后果：

- 不能被浏览器、代理、CDN 缓存；
- 不能收藏、不能分享链接、不能刷新重放；
- 地址栏里直接打不开，调试成本变高；
- **排查事故时，光看日志无法区分这次请求有没有改数据**——这一条在故障现场代价很大；
- 预取、重试等机制会误伤。

**适用条件（请保留，不要简化成"读操作必须用 GET"）**：确实存在合理例外——查询条件极长超出 URL 长度限制、查询条件含敏感信息不希望进入浏览器历史与访问日志。这时用 POST 做查询是可以接受的，但它应当是**你有意识做出的例外**，并在代码或文档里说明理由，而不是默认写法。

讲：

> 今天这两条，加上你刚装好的四处观察点，构成了同一个主题：**让系统能够被诊断**。
>
> 对比一下：AI 生成的版本不是"不能跑"，是"跑坏了没人知道"。而你现在有能力提出这个要求了。这就是今天你多出来的那点东西。

## 十、C 档结论卡：今天不展开但你要知道结论的部分

**约 3 分钟。快速带过，明确说明"这几页是给你课后查的，不要求今天理解推导"。**

请做成一页速查卡：

| 问题 | 结论 | 展开的位置 |
|---|---|---|
| 域名怎么变成 IP | DNS 查询，有多级缓存；查不到时浏览器报 `ERR_NAME_NOT_RESOLVED`，**这类错误没有 HTTP 状态码** | 《计算机网络》 |

| 本地开发为什么没有反向代理 | 开发环境直连 uvicorn；生产环境前面通常有 Nginx 等，它负责 TLS、静态文件、转发 | 第 16 次课 |

### 作业三：按规格补两个端点（**规格如下，请严格按规格实现**）

> 这份规格的写法本身就是学习内容。注意它写了什么：方法、路径、参数与约束、成功响应、每一种失败响应及其状态码、以及额外要求。以后你让 AI 写代码时，给的应该是这种东西，而不是"帮我写个查询接口"。

```
端点 1：获取单个问题
  方法与路径：GET /questions/{qid}
  路径参数：qid，整数，≥ 1
  成功：200
        {"id": 1, "title": "...", "body": "...", "created_at": "..."}
  不存在：404
        {"code": "question_not_found", "message": "...", "request_id": "..."}
  qid 非整数（如 /questions/abc）：422
        —— 这个响应由框架自动产生，本次课只要求你能说出它是谁生成的、在链路哪个环节产生
  响应头：必须包含 X-Request-ID
  日志：必须有带同一 rid 的进入与离开两条记录

端点 2：健康检查
  方法与路径：GET /healthz
  成功：200，{"status": "ok", "db": "ok"}
  数据库不可用：503，{"status": "degraded", "db": "down"}
  要求：只执行 SELECT 1，不查业务表；任何情况下都不得抛出未捕获异常
```

**健康检查这个端点值得多说一句**：数据库断了应该返回 503（服务暂时不可用）而不是 500 或 200。因为 503 是告诉运维系统与负载均衡"我现在不健康，别把流量给我"。这个端点在第 16 次课部署时会真正派上用场。

2. 传入的 `X-Request-ID` 是否被沿用而不是被覆盖；
3. 日志中每个请求是否有配对的进入/离开记录且 rid 一致；
4. 两个新端点的方法、路径、状态码是否符合规格；
5. 源码中是否还存在硬编码的数据库密码与 API 密钥（今天最低限度改为 `os.getenv` 读取，并提交 `.env.example`；`.env` 必须在 `.gitignore` 中）。
