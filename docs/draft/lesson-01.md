## 二、解剖台：能运行，还缺什么证据

**课堂 10 分钟。** 使用 `v1_ai_raw.py` 实际源码，不另造一份路径、数据或启动命令不同的反例。

教师做三件事：普通搜索、缺失详情、查看终端和响应。读代码时指出 SQL 执行、成功返回、缺失分支所在位置。

| 观察 | 现在能说什么 | 还不能说什么 |
|---|---|---|
| 搜索返回 200 与数据 | 此次查询完成并返回数据 | 所有搜索都正确 |
| 缺失详情返回 `success:false` 但状态 200 | 正文与 HTTP 语义不一致 | 请求因此无法关联 |
| uvicorn 有访问日志 | 能看到一部分请求信息 | 已有完整的应用内部经过 |
| 查询和异常没有统一关联字段 | 并发排查需要更多证据 | AI 生成的代码必然不可观察 |

不把反例说成“所有失败都返回 200”：未处理的 SQL 错误仍可能返回 500。观察不足也不是“任何信息都没有”；访问日志、响应正文和定向测试仍然有价值。

- 拼接 SQL：只在隔离反例保留；后续教师模板用参数化语句，第六课解释原理。
- 全字段返回：第三课出口契约。
- 配置集中与约束：第四课；今天保留环境变量读取。
- 异常路径观测：第四课认识处理器位置并提供最小补齐，第五课深化日志与响应头的时序。

## 三、链路图：位置不是一条连续的 Python 调用栈

**课堂 10 分钟。**

```text
浏览器 → 名称解析与连接 → 反向代理 → ASGI 服务器
       → 中间件 → 路由与参数解析 → 应用代码 → 数据库
       ← 响应与浏览器渲染
```

代理在本地直连环境中灰显；实际部署可以有 CDN、负载均衡和多进程。DNS/TCP/TLS 只给位置，不讲内部机制。

| 环节 | 谁负责 | 典型现象 | 观察位置 |
|---|---|---|---|
| 请求构造 | 页面代码 / 表单 | 未触发、URL 或方法错误 | Network 是否有目标请求、Console |
| 名称解析与连接 | 浏览器、操作系统、网络 | 解析失败、连接拒绝、证书问题 | 浏览器诊断、curl 详细信息 |
| 代理 | 部署设施 | 502/504、资源转发问题 | 代理日志；本课无此层 |
| ASGI 服务器 | uvicorn | 端口未监听、进程退出 | 启动终端 |
| 中间件 | 应用与框架 | 提前拒绝、响应头缺失 | 进入 / 离开日志 |
| 路由与参数解析 | 框架 | 404、405、422 | 响应体、路由声明、后续 `/docs` |
| 应用代码 | 项目实现 | 结果错误、异常 | 带 id 日志、断点状态 |
| 数据库访问 | 应用驱动与数据库 | 连接失败、SQL 错误或慢查询 | SQL 日志、执行事件 |

**判据一：没有可见状态码，不足以证明请求没有到达应用。** 请求可能未发出，也可能执行后连接中断、浏览器拒绝向脚本暴露响应，或被取消。结合服务端日志和 id 才能进一步定位。有 HTTP 状态也只证明收到了某一响应，不保证响应来自目标应用，可能来自代理或缓存。

**判据二：先找目标请求，再判断下一步。** 不把“浏览器没显示结果”直接等同于“后端没有数据”。第二课会继续区分请求、解析和渲染阶段。

## 四、观察点①：请求与响应

**课堂 10 分钟；URL 与 curl 参数表为 A 档课后查阅。**

在示例目录、数据库已初始化的前提下，按 README / Makefile 启动 v1 或 v2。以下是课堂 v2 阶段的请求：

```bash
curl -i -X POST 'http://127.0.0.1:8000/getQuestions?keyword=react'
```

在 Network 或 curl 中指出：方法、路径与查询串、请求头、请求体；状态码、响应头、响应体。GET 查询通常没有请求体；今天不要把 HTTP/1.x 的文本起始行、头、空行、正文结构当作 h2/h3 的线上字节格式。

URL 卡：scheme / host / port / path / query / fragment；`#fragment` 不作为 HTTP 请求目标发送给服务器。查询串中特殊字符需要编码，第二课用 `URLSearchParams`。

讲：“用 curl 重发相同参数”是另一次执行，可以用于复现，**不是第一条浏览器请求的同一次执行**。四处合流要只发一次目标请求，把它停在断点，再继续取得响应与日志。

`/docs` 是发请求的工具；它展示的声明和自动 OpenAPI 在第三课解释。若其 CDN 资源不可用，换 curl，不声称当前工程已配置本地 Swagger 资源。

## 五、观察点②：先看到交织，再加入 request-id

**课堂 12 分钟。**

1. `TRACE_MODE=plain DEMO_DELAY_MS=80` 启动 `v2_traceable`，先单请求。
2. 运行现有 `bench.py`，在十条有限并发请求中混入一条自己的请求，观察交织。
3. 再切到 `TRACE_MODE=trace`，保持其他条件，重新观察并按目标 id 筛选。

80ms 是人为教学延迟，不是数据库性能。脚本有有限请求数与超时，不保证所有电脑都在固定秒数完成。学生若已凭其他字段定位成功，应说明依据，不强迫“所有人一定找不到”。

当前 request-id 的关键实现节选：

```python
import re
import uuid

supplied = request.headers.get("X-Request-ID", "")
rid = supplied if re.fullmatch(r"[A-Za-z0-9._-]{1,64}", supplied) else uuid.uuid4().hex
request.state.request_id = rid
```

request-id 是本课单请求关联标识，不直接等同于分布式 trace-id。完整分布式追踪还有传播协议、span、采样等机制。客户端可以重复传同一 id，本课取证要为每次目标执行使用新值；不要声称只凭相同 id 就能无条件证明唯一一次执行。

课堂中间件先保留正常路径：

```python
logger.info("[%s] --> %s %s", rid, request.method, request.url.path)
response = await call_next(request)
logger.info("[%s] <-- %s", rid, response.status_code)
response.headers["X-Request-ID"] = rid
return response
```

这是函数体节选，完整导入、计时和运行开关见 `v2_traceable.py`。正常路径包括框架已处理的 404/422 等，不只包括 2xx。

**边界演示 `/boom`**：未处理异常使 `call_next` 抛出，后半段不执行。进入日志仍可存在，但缺离开日志、普通 500 缺响应 id 头。不要说“完全查不到”。第四课定位异常处理器层次并提供最小补齐，第五课复演 `finally` 日志和外层 500 响应头的不同职责；只加处理器不保证全部修好。

## 六、观察点③：当前栈帧与变量一起看

**课堂 10 分钟。**

用无 `--reload` 的调试配置启动 v2，在 `conn.execute` 前下断点。发一次目标请求，停住后同时看 Call Stack 与 Variables。

本例端点是同步 `def`，由框架在线程池执行。实际栈可能包含端点、AnyIO worker 与 Python 线程入口，**不要求出现连续的端点→中间件→uvicorn 栈**。

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| 当前调用栈 | 当前线程如何调用到此处 | 跨线程、跨任务、跨网络的完整请求链 |
| 局部 `rid`、`keyword`、`page` | 这一停点处理的目标与参数 | 所有前后步骤均已成功 |
| 代码停在查询前 | 尚未执行该行 SQL | 整个系统没有其他请求 |

链路图描述职责与经过；调用栈描述当前执行上下文。两者可以对应某一位置，不是一张图的两种截图。不能为了“完整栈”把同步端点改成不必要的 async。

操作只讲继续、步过、步入、停止，以及两个面板。若 30 秒内不能停住，用已标注来源的录屏或 DAP 采集结果说明原理；DAP 数据不是 IDE 界面截图，作业仍须补本人停点证据。

## 七、观察点④：SQL 日志不是天然带 id 的请求记录

**课堂 6 分钟。**

`SQL_ECHO=1` 打开现有引擎回显，暂停并发与其他自动请求后，从查询前断点继续。观察语句、参数呈现方式和返回行数。

```python
logger.info("[%s] sql:begin search", rid)
rows = conn.execute(statement, parameters).fetchall()
logger.info("[%s] sql:done rows=%d", rid, len(rows))
```

上面是参数化模板中的通用形状；v2 反例仍使用拼接 SQL，要标清阶段，不能把未完成的修复说成已完成。

- `echo=True` 默认不带 request-id。暂停并发后，用带 rid 的边界日志限定这次执行的证据范围。
- 并发时“夹在两行日志之间”不保证 SQL 属于同一请求，不能强行做四处 id 全部出现的截图。
- 一条 SELECT 之外可能出现 BEGIN/ROLLBACK 等事务日志。日志行数、SQL 执行次数、返回行数不是同一指标。
- 第七课会测 ORM 查询数，但不预先规定一定是 101 条；数据关系、加载策略和计数范围都会改变结果。
- 不记录真实凭据、敏感正文和不必要的用户信息；日志也要有权限边界。

## 八、唯一现场必做：同一次执行的四处合流

**课堂 10 分钟。**

步骤：暂停噪音 → 新 id → 查询前断点 → 发一次请求 → 保存栈与局部变量 → 继续 → 保存响应、应用日志和 SQL 证据。请求停住时 curl 没有返回是正常现象；给调试留足超时。

```bash
curl -i -X POST 'http://127.0.0.1:8000/getQuestions?keyword=react' \
  -H 'X-Request-ID: stu-demo-unique-01'
```

此命令属于课堂 v2，不用于第二课 M0 搜索。

| 证据 | 截取范围 | 一句话解释 |
|---|---|---|
| 报文 | 目标请求与响应 id、状态 | 客户端实际获得什么 |
| 应用日志 | 同 id 的进入、查询、离开 | 应用记录了哪些经过 |
| 断点 | Call Stack + Variables 中的 rid | 当前线程在何处处理该请求 |
| SQL | 带 id 的边界日志与实际语句 | 在已暂停并发条件下执行了什么 |

## 九、回收反例：状态码与方法表达意图

**课堂 16 分钟。**

### 9.1 `200 + success:false` 的问题是什么

仍然可以用 request-id 关联，也可以读正文识别错误。问题是只按 HTTP 状态统计和决策的工具会得到错误信号。

| 使用者 | 条件化后果 |
|---|---|
| 仅按状态计错误率的监控 | 业务失败可能计为成功 |
| 配置为读取探针状态的负载均衡 | 错误探针结果会误导转发策略 |
| 按状态与缓存头决策的缓存 | 若满足缓存条件，可能复用不该复用的结果 |
| 客户端 | 只检查 HTTP 成功不够；还应验证所需结果形状 |

不能说“返回 200 必定缓存”“任何 500 都会摘除实例”“Network 绿色就是业务正确”。

2xx 表示按 HTTP 语义报告成功；4xx 表示请求条件等不满足；5xx 表示服务端未能完成请求。重试取决于具体状态、失败原因、幂等性、`Retry-After` 与退避。429 可能等待后重试；有副作用的请求不能因 5xx 就盲目重放。

### 9.2 普通读取优先 GET

M0 的关键词搜索改为 `GET /questions`，详情改为 `GET /questions/{qid}`。这是明确的作业契约迁移，不要求学生现在设计全部 REST API。

GET 可直接打开、收藏与分享，更自然地采用通用缓存策略。安全语义是“不请求业务状态变化”，并不禁止日志与计数等附带行为；方法也不能证明实现真的没有副作用。

POST 查询有合理例外，如复杂长条件、不希望条件进入 URL 历史。POST 并非协议上绝对不可缓存，但通用支持有限；POST 不加密正文，也不保证正文不被日志记录。第八课再系统讨论资源、幂等与更新。

## 十、课后结论卡

**课堂只用 2 分钟指明阅读位置。**

| 主题 | 结论与边界 |
|---|---|
| DNS | 解析与缓存影响到达过程；解析失败不是 HTTP 状态码 |

| 端点 | 必须兑现的契约 |
|---|---|
