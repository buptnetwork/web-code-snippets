## 1. 现状陈述（8′）——三句话，不评判学生

1. 你们已经能让 AI 生成一个能跑的 Web 项目，这个能力是真的，不需要贬低。
2. 但"能跑"和"能交付"之间，隔着一批你现在还没有词汇去描述的东西。
3. 本课程不教怎么让 AI 生成代码，教**怎么向它提要求、怎么验收它的产出、以及它错了怎么找出来**。

板书一句话定位：

> **生成不再是瓶颈，判断成了瓶颈。这门课站在瓶颈的另一侧。**


一个你大概已经经历过的场景

你向 AI 描述了一个需求，它给了你一个能跑的项目。你部署给同学用，然后遇到下面某一种情况：

- 页面上"提交"点两次，帖子发了两条；
- 你改了代码，自己看是新的，别人打开还是旧的；
- 列表页数据一多就卡，但你不知道慢在哪一层；
- 有人把 URL 里的 `id` 改成别人的，就看到/改掉了别人的数据；
- 报错只有一句 `Internal Server Error`，你不知道去哪里看；
- 你让 AI"修一下这个 bug"，它改了三个文件，其中两个把别的功能弄坏了。

这些问题的共同点是：**它们都不是"生成代码"能力不足造成的**。AI 生成的代码语法正确、结构像样、甚至比你手写得漂亮。问题出在**没有人向它提出这些方面的要求，也没有人有能力检查它是否满足**。

## 2. 案例场景 A：10 分钟找错

### 操作流程

1. 展示下面这段代码（纸质或在线），学生**独立**思考，想一下"你认为有问题的地方 + 为什么"。
2. 公布答案，逐条说明"后果是什么"。

### 展示给学生的代码（AI 生成，能跑）

```python
from fastapi import FastAPI, Depends
from sqlalchemy.orm import Session
from database import get_db
from models import User

app = FastAPI()

OPENAI_API_KEY = "sk-proj-4f9c2a17bd3e8a55c1"
DB_PASSWORD = "postgres123"

@app.post("/getUserPosts")
def get_user_posts(user_id: int, db: Session = Depends(get_db)):
    user = db.query(User).filter(User.id == user_id).first()
    result = []
    for post in user.posts:
        author = db.query(User).filter(User.id == post.author_id).first()
        result.append({
            "id": post.id,
            "title": post.title,
            "content": post.content,
            "author": author,
        })
    return {"success": True, "data": result}

@app.post("/deletePost")
def delete_post(post_id: int, db: Session = Depends(get_db)):
    post = db.query(Post).filter(Post.id == post_id).first()
    db.delete(post)
    db.commit()
    return {"success": True}
```

### 答案卡（公布时用）

| # | 缺陷 | 后果 | 
|---|---|---|---|
| 1 | 密钥硬编码在源码 | 一旦推到仓库即泄漏，且无法分环境 | 
| 2 | 读操作用 `POST`，URI 用动词 | 不可缓存、不可分享链接、语义错误 | 
| 3 | 返回整个 `author` 对象 | **密码哈希、邮箱随响应泄漏** | 
| 4 | 无 `response_model`，返回裸 dict | 契约不可知，前端无法生成类型，改坏无感 |
| 5 | 循环内查询（N+1） | 100 条帖子发 101 条 SQL，列表页越用越慢 |
| 6 | `user` 可能为 `None` 未判断 | 500 崩栈，且异常直接暴露给用户 | 
| 7 | 两个接口**都没有鉴权与归属校验** | 任何人传 `post_id` 就能删别人的帖（IDOR） | 
| 8 | 错误也返回 `200 + success:false` | 前端、日志、监控、重试全部失效 | 
| 9 | 删除无幂等考虑、无软删除、无审计 | 重试与误操作不可挽回、无法追责 | 

**收尾话术**（重要，避免变成打击）：

> 这段代码没有语法错误，AI 也没有"胡说"。它的问题全部属于同一类：**你没提的要求，它不会替你补。** 班级平均找到 X 条，期末我们会用同类题重测一次，对比前后。

## 3. 案例场景 B：两个提示词的对比

用同一个模型跑两次，对比输出。

**提示词 1（学生的典型写法）**

> 帮我写一个问答社区的发帖接口，用 FastAPI。

**提示词 2（本课程结业时应该能写出的）**

> 用 FastAPI 实现"发布提问"接口，遵守以下约束：
> 1. 分层：路由只做参数绑定与响应，业务逻辑放 `services/`，数据访问放 `repositories/`；禁止在路由中直接使用 Session。
> 2. 契约：定义 `QuestionCreate` / `QuestionOut` 两个 Pydantic 模型，端点声明 `response_model`；**输出模型不得包含作者的邮箱与密码字段**。
> 3. 错误：校验失败返回 422，未登录 401，无权限 403，标题重复 409；错误响应统一为 `{code, message, request_id}`。
> 4. 授权：必须通过 `get_current_user` 依赖取得当前用户，作者取自会话而非请求体。
> 5. 数据：标题非空且 ≤ 200 字符，标签数 ≤ 5；数据库层需有相应约束。
> 6. 一次请求一个事务；不得在循环内查询数据库。
> 7. 不要引入新的第三方依赖。
> 验收标准：附 3 条 pytest 用例，分别覆盖成功、未登录、标题超长；`tsc`/`ruff` 无警告。


**结论（板书）**：

> **你能提出的要求，上限等于你掌握的专业词汇量。** 提示词工程的天花板不是话术，是概念。

## 4. 三张表（12′）

**表 AI时代Web开发需要的能力**
 成本结构变了，稀缺的东西也变了

写出一段"能跑的代码"的成本正在趋近于零。当某种能力变得极其便宜时，价值会转移到与它**互补、但没有一起变便宜**的能力上。对 Web 开发来说，这些互补能力是五项：

| 能力 | 它要回答的问题 | AI 单独做不好的原因 | 本课程中的训练与考核 |
|---|---|---|---|
| **需求规格化** | 这个功能"做完了"的标准是什么？边界情况怎么算？ | 你不说，它就按最常见路径猜 | 每次作业先写规格再生成；第 9 次课"规格先行" |
| **约束表达** | 分层、错误契约、事务边界、授权要求怎么写成它能执行的话？ | 约束来自你的项目语境，不在它的训练分布里 | 每课末的"提示词约束骨架"；仓库级 AI 规约文件 |
| **验收判据** | 怎么判断它交的东西合格？靠肉眼还是靠机器？ | 它不会主动为自己设关卡 | 每课"评审清单"；第 9 次课 CI 四道门禁 |
| **缺陷定位** | 出问题了，在链路的哪一层？怎么最快缩小范围？ | 它看不到你的运行时、日志和数据 | 请求全链路追踪；故障定位四步法；植入 bug 实验 |
| **方案取舍** | Session 还是 JWT？SSR 还是 SPA？加不加索引？ | 取舍依赖你的约束条件与代价承受度 | 每个技术决策写 ADR；口试要求辩护 |

一句话总结这门课的位置：

> **它不教你怎么让 AI 生成代码，它教你怎么向 AI 提要求、怎么验收它的产出、以及它错了怎么找出来。**

**表 2：学习关注点的六个转变**

这门课与三年前的"Web 全栈"课程内容重叠不到一半。请在预习和上课时带着这六个转变：

| 从 | 到 |
|---|---|
| 记住框架 API 怎么写 | 建立**心智模型**：一个请求经过哪些环节，每个环节谁负责、失败什么样、在哪观察 |
| 追求"能跑" | 追求"**可解释、可验收、可回滚**"——你要能说出每一行为什么这样写 |
| 从零手写代码 | **读、改、诊断、决策**：课堂上大量时间用来读别人（包括 AI）写的代码 |
| 遇到报错就换写法/问 AI 重写 | 用**方法**定位：复现 → 最小化 → 二分 → 假设验证 |
| 靠自己肉眼审查 AI | 靠**机器把关**：类型检查、lint、测试、契约校验进 CI，让不合格的产出根本进不来 |
| 学具体技术栈 | 学**长半衰期的原理 + 判据表**，框架只是载体（本课用 FastAPI/React，换栈仍成立） |
