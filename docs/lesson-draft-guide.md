# 教学底稿编写指南

> **面向教师**：你交的是一份能帮助自己上课的教案，不是 PPT 说明书，也不是给机器填写的表单。
> 本指南适用于计算机软件类课程；职责、归档和验收以[通用制作流程](authoring-workflow.md)为准。你不必阅读工具实施文档。

## 1. 一次交什么

通常交完整一次课的底稿，让 AI 看见目标、前后关系与时间安排；不必等所有图片或演示数据齐全。

课件定位为**内容详实型**，重点是教学内容有价值、页面美观且读得清。无需为了“像 slides”删去核心解释，也不必安排大量师生互动；AI 通过信息分层、图示和必要分页组织内容。

按**教学单元**写，而不是按页写。一个单元可以是概念、问题、任务、实验或调试过程；一个单元做几页，由 AI 决定。

正文写你希望学生看到、理解或完成的内容；讲稿写你要怎么讲；特殊意图用自然语言补充即可：

- “两个方案要同时在场，用同一组数据解释差别。”
- “先讲规则，再用运行结果说明为什么成立，最后标明适用条件。”
- “这段需要先预测再揭晓，不要提前露出答案。”（仅在确有互动意图时说明。）

字段名、排版形式都不必统一，写成散文也可以。已有稳定编号就保留，没有则由 AI 补充；教师也可以直接用标题讨论。

对关键内容，尽量说清“结论是什么、为什么、在什么条件下成立”；涉及实现时，用同一实例连接概念、接口、代码与结果。若中途回顾语言或工具知识，说明之后要回到哪个原问题。已有材料不完整也可交付，由 AI 标出缺口，不要求另填检查表。

## 2. 一个跨课程写作范例

下面是“现代 Web 开发技术”的**单元写作示例**，不是完整次课，也不代表已有示例工程或已完成课堂实测。不预设前后端框架。

```markdown
## 异步请求与界面状态

学生已经会处理表单提交，但容易把“收到响应”当成“业务成功”。
这个单元约 12 分钟，目标是能区分加载中、成功、HTTP 错误和网络失败，
并根据请求/响应与界面状态定位问题。

内容：
用户提交查询后，先进入加载中，避免重复提交。
成功响应时展示结果；HTTP 错误时展示对应提示；网络失败时提示重试。
结束后不能一直停在加载中。

演示：
同一个查询，依次展示成功、HTTP 500、没有拿到可用 HTTP 响应三种结果。
同时展示浏览器 Network 记录与界面状态，依次运行并解释对应关系。
HTTP 500 也是响应，不能和网络失败混为一谈。
界面提示与恢复策略按本示例约定处理，不把它们说成所有应用的唯一设计。

材料：
使用独立的前后端演示项目，提供表单提交处理与接口处理代码的文件位置。
请求是 GET /api/items?q=book。
成功响应为 200 和 {"items":["book"]}；故障场景在本地模拟 500 或连接失败。
图只需表现“提交 → 请求 → 响应或失败 → 界面更新”的关系。

讲：从提交处理函数沿着请求、响应分支讲到界面更新，解释加载态的起止。
收到 500 时，服务器已经回答，但不是成功结果。
课件保留三种情况的证据与结论，便于课后对照。

解析：展示“请求结束了但按钮一直禁用”的实现，指出遗漏的恢复步骤及修复结果。
备用：现场演示超过 30 秒就切到预先准备的状态截图，截图注明模拟场景。
```

这里最重要的不是字段，而是**学会什么、如何解释、用什么证据支撑、结论适用于哪里**。预测、讨论和练习按教学需要选用，不是每个单元的必填环节。源代码与运行条件另行提供，不必把完整项目贴进底稿。

对照一个数据结构单元，仍用同样的写法：

```markdown
## 顺序查找为什么与输入有关

目标：能说出第一次命中、最后一次命中和未找到时的比较次数。
内容：从下标 0 开始，找到第一个相等元素就返回下标，未找到返回 -1。
例子：数组 [3, 8, 5, 9]，分别查找 3、9、7。
要求：逐步走代码，展示三种情况的比较次数，并解释退出位置为何不同。
代码：提供独立的查找实现和三个测试用例，课件只展示查找主体。
讲：查找的是同一个数组，程序也没换，为什么比较次数不同？
```

这也是**写作示例，未在本轮运行验证**。单文件算法与多文件 Web 演示的差别在素材和验证方式，不在教师需要学习的新格式。

## 3. 开头用几句话说明全局

不要求四张表，也不要求填满字段。你知道什么就写什么，例如：

> 本次课 90 分钟，留 5 分钟缓冲。重点是请求状态和错误定位；超时就压缩框架 API 罗列，保留请求到界面更新的完整实例。最难讲清的是“有响应但不成功”，请优先让我看这一段演示。

AI 会从已有内容整理时长、重点、压缩预案和素材需求；只追问影响教学正确性或制作方向的缺口。

单个讲授单元超过约 10–15 分钟或 8–10 条要点时，可以考虑拆分。连续实验不必为了这个数字打断，但要说明停顿或检查结果的位置。

不必指定“高光页”，也没有每课必须几个的要求。若有特别难讲清的地方，说明原因；重点可以通过图、交互、实测或调试表达，不一定增加动画。

## 4. 讲稿可以长，也可以是提纲

口语讲稿有助于区分上屏信息和教师解释，但**不要求逐字稿**。几句提示、提问、停顿或操作提醒也有用：

> 打开 Network，指着状态码解释；再对照页面提示，说明 HTTP 错误和没有可用响应的区别；最后回到处理函数，标出两个分支。

AI 将讲稿或提纲分配到正文、演讲者备注与演示步骤，保持教学原意。核心解释、必要条件和例题解析要能从成稿中查到；备注补充口语展开、节奏和操作提醒，不独占学生理解所需的信息。没有讲稿也不会退稿，AI 应把推断的关键讲述意图拿出来确认。

## 5. 图、代码和演示素材怎么给

**图与表**只需说明要素、关系、数据和用途。例如“请求从浏览器到服务端再返回，区分 HTTP 错误和连接失败两条路径”。技术画法与配色交给 AI。提供截图时说明要看的字段或区域，AI 可保留环境概览并放大关键证据，避免学生从整屏截图里找小字。

**外部素材**提供源文件或可访问链接；事实性材料尽量附标题、来源、日期。缺素材会明确留占位；不确定真伪的内容需核实，不能直接当作事实上屏。

素材较多时，用一句话分清“缺了讲不下去”“可后补”“课堂手画或使用备用材料”，不要求再维护一张表。

**可运行示例**提供独立文件、多文件工程或外部仓库的具体版本。已经有源码，就告诉 AI 在哪里；没有时说明期望行为，由 AI 按课程约定补充并验证，不要求教师先写完整代码。伪代码、短片段可以直接贴在文中。

**故障与阶段示例**说清楚是预期错误、起始版还是修复版。可运行的反例也要验证预期失败；多个阶段各有用途，不与最终实现混淆。

若有现场操作，按需要补充已有信息：

- 使用什么环境和依赖版本，如何启动、如何确认运行正确。
- 演示开始时的数据和界面状态，如何复位后重演。
- 是否需要网络；失败或超时时改用哪份截图、录屏、模拟结果或离线材料。

AI 优先读取项目现有说明、依赖和脚本，不要求你重复抄写。环境未确认就标“待确认”，模拟数据明确标注。使用隔离演示数据，不提供生产账户、真实凭据或敏感数据。

## 6. 交出去后，你会参与哪些决定

1. **先收到审读结果**：AI 核对主线是否闭环、结论前提、课后可读性、前后引用和时长。明显机械错误可修正并回报；事实冲突、内容取舍或顺序变化请你裁决，不因格式问题退稿。
2. **再看关键表达**：AI 给出简短分页方案，优先让你看最难、最容易返工的图示或演示。你确认教学意思是否准确，不必逐页批准排版。
3. **分批收到成稿**：AI 看过完整底稿后，在同一最终工程内逐步完成。页面可以分批做，教学上下文不能只看半份。
4. **收到验收说明**：说明实际检查了哪些内容、仍有哪些占位及未验证项。构建通过不等于示例行为、点击顺序、备注和 PDF 都通过。

开始落地最终工程时，底稿就会冻结并标注“已归档 / 不再更新 / 以最终课件工程为准”及成稿位置；若关键页验样已经落地，此时就移交。后续批次仍可参考归档快照，但补充和修改只进入最终工程。

**归档不等于验收完成，也不代表底稿永远准确。** 下一轮备课应从最新课件工程提取内容，归档底稿只作历史参考。

## 7. 修改与课后反馈

直接用自然语言说：

- “这里有结论但缺原因，补一个实例和适用条件。”
- “错误状态加一个可复现的例子，并核对讲稿。”
- “这段前后端协作按请求经过的阶段展开，不要强行挤在一页。”
- “截图里的关键数值太小，放大证据区域，不要只缩小旁边的文字。”

AI 先定位相关内容与引用，再就地修改并检查。不要回头修改归档底稿，也不需要学习课件语法。

课后只需说三件事：**哪里超时、哪里没学会、哪里呈现妨碍讲解**。这些反馈直接用于修订最终工程，比再填一套评价表更有用。
